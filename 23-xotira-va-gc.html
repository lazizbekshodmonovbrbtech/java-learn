Xotira va Garbage Collector.

Java'da xotirani qo'lda bo'shatmaysiz — GC qiladi. Lekin "avtomatik" degani "o'ylamasa bo'ladi" emas: memory leak, OutOfMemoryError, uzun GC pauzalar — hammasi shu yerdan. Bu modulda obyektlarning butun hayotini ko'rasiz.

01

Heap: obyektlar qanday "qariydi"

Gipoteza: obyektlarning ko'pi yosh o'ladi (so'rov tugadi — DTO kerak emas). Shuning uchun heap avlodlarga bo'lingan. Yangi obyekt Eden'ga tushadi. Eden to'lsa — Minor GC: tiriklar Survivor'ga ko'chadi, o'liklar tashlanadi. Bir necha GC'dan omon qolgan — Old'ga.

"+ 6 obyekt" — so'rov keldi, DTO/String'lar yaratildi. Eden to'lganda Minor GC bo'ladi.
Suhbatda so'raladi
Minor GC — Young (Eden+Survivor), tez, tez-tez. Major/Full GC — Old ham, sekin, "stop-the-world" uzunroq. Survivor ikkita (S0/S1) — ko'chirish (copying) fragmentatsiyasiz bo'lishi uchun: har GC'da tiriklar bittasidan ikkinchisiga ko'chadi, birinchisi to'liq bo'shaydi. Yosh chegarasi (tenuring threshold) default ~15, JVM moslashtiradi.
02

GC nimani "axlat" deydi? Reachability

GC hisoblagich sanamaydi. U ildizlardan (GC roots: thread stek'idagi lokal o'zgaruvchilar, static maydonlar) boshlab havolalar bo'ylab yuradi. Yetib bo'lmagan hamma narsa — axlat, hatto bir-biriga havola qilsa ham. Havolani bosib uzing.

obyektni bosing → unga kelgan havola uziladi
Yashil — GC roots (stek o'zgaruvchisi, static). Binafsha — heap obyektlari. Hozir hammasi yetib boriladigan (reachable).
Roots.java
static Map<String, Mijoz> kesh = new HashMap<>();   // GC root: static → hech qachon o'lmaydi

void ishla() {
    Mijoz m = repo.top(1);        // GC root: stek'dagi lokal o'zgaruvchi
    m.manzil = new Manzil();        // m orqali yetib boriladi
    m = null;                       // havola uzildi → Mijoz VA Manzil axlat (Manzil'ga boshqa yo'l yo'q)
}                                   // metod tugadi → stek freymi yo'q → hamma lokal havola yo'q
// System.gc() — faqat "iltimos", kafolat yo'q. Ishlab chiqarishda chaqirmang.
03

Memory leak: GC bor, lekin xotira tugaydi

Java'da leak — "unutilgan havola": obyekt kerak emas, lekin kimdir (static kesh, listener, ThreadLocal) uni ushlab turibdi. GC uni tirik deb hisoblaydi. Har so'rovda static keshga qo'shamiz va hech qachon o'chirmaymiz:

-Xmx (maksimal heap)
java.lang.OutOfMemoryError: Java heap space
Grafik — heap band hajmi. Arra tishlari — GC bo'shatgan joylar. Leak'da har tish avvalgisidan balandroq: baseline o'sib boradi. Bu — leak'ning klassik belgisi.

Tipik leak manbalari

static List/Map — cheksiz o'sadi
Listener/callback — unregister yo'q
ThreadLocal — pool'da remove() yo'q
Ochilmagan resurs — Connection, Stream
Ichki (non-static) class → tashqi obyektni ushlaydi
HashMap kaliti mutable — topib o'chirib bo'lmaydi

Yechim va aniqlash

Chegarali kesh: Caffeine (maximumSize, expireAfter)
WeakHashMap / WeakReference — GC olib ketishi mumkin
try-with-resources
-XX:+HeapDumpOnOutOfMemoryError
jcmd <pid> GC.heap_info · jmap -histo
Heap dump → Eclipse MAT / VisualVM: "Leak suspects"
04

GC algoritmlari: pauza vs o'tkazuvchanlik

Hamma GC "stop-the-world" (STW) qiladi — dastur to'xtaydi. Farq: qancha va qanchalik tez-tez. 8 GB heap uchun taxminiy pauza:

Bank API'da SLA 200ms bo'lsa, 2 soniyalik Full GC = timeout. Java 17+ default G1: heap'ni regionlarga bo'lib, eng "axlatli" regionlarni birinchi yig'adi (Garbage-First), pauza maqsadi -XX:MaxGCPauseMillis=200. ZGC — heap hajmidan qat'i nazar <1ms pauza, parallel (concurrent) ishlaydi, CPU ko'proq yeydi.

OOM — Error, ushlab davom etish odatda ma'nosiz. Dump oling, tahlil qiling.

06

Suhbat savollari

?JVM xotira sohalari qaysilar?
Heap (obyektlar; Young: Eden+S0+S1, Old), Metaspace (klass metadata, Java 8+ native xotirada, ilgari PermGen), Thread stack (har thread'ga freymlar, lokal o'zgaruvchilar, primitivlar va havolalar), PC register, Native method stack, Code cache (JIT kompilyatsiya qilingan kod). String pool — Java 7+ heap'da.
?GC qanday ishlaydi? Mark-sweep-compact?
1) Mark: GC roots'dan (stek lokal o'zgaruvchilar, static maydonlar, JNI, aktiv thread'lar) havolalar bo'ylab yurib, tiriklarni belgilaydi. 2) Sweep: belgilanmaganlarni bo'shatadi. 3) Compact: tiriklarni zichlab fragmentatsiyani yo'qotadi. Young'da 'copying' (tiriklarni Survivor'ga ko'chirish — o'liklar ko'p bo'lgani uchun arzon). Reference counting ishlatilmaydi — siklik havolalar muammo emas.
?Nega heap avlodlarga bo'lingan?
'Generational hypothesis': ko'p obyektlar tez o'ladi (so'rov davomidagi DTO, String). Yosh avlodni tez-tez, kichik, arzon GC qilish (Minor) — tiriklari kam, ko'chirish oson. Uzoq yashaganlar Old'ga o'tadi va kam yig'iladi. Natija: umumiy pauza kam.
?Minor va Major/Full GC farqi?
Minor — faqat Young (Eden to'lganda), tez (ms), tez-tez. Major — Old avlod; Full — butun heap + Metaspace, sekin (100ms–soniyalar), STW uzoq. Tez-tez Full GC — Old to'lib borayotgani belgisi: leak, katta kesh, yoki -Xmx kichik.
?Memory leak Java'da qanday bo'ladi? Qanday topasiz?
Kerak bo'lmagan obyektga havola saqlanib qoladi: static kolleksiya, unregister qilinmagan listener, ThreadLocal.remove() yo'q, yopilmagan resurs, non-static ichki klass. Belgisi: GC'dan keyin heap baseline o'sib boradi, oxiri OOM. Topish: -XX:+HeapDumpOnOutOfMemoryError, heap dump → Eclipse MAT 'dominator tree / leak suspects', jmap -histo bilan klasslar sonini solishtirish.
?Strong, Soft, Weak, Phantom reference?
Strong — oddiy havola, hech qachon yig'ilmaydi. Soft — xotira yetishmasa yig'iladi (kesh uchun). Weak — keyingi GC'da yig'iladi agar faqat weak havola qolsa (WeakHashMap, kanonik map). Phantom — obyekt yig'ilganini bilish uchun (resurs tozalash, Cleaner API). finalize() — deprecated, ishlatmang.
?G1 va ZGC farqi? Qaysi birini tanlaysiz?
G1 (default 9+): heap'ni ~2048 regionga bo'ladi, eng ko'p axlatli regionlarni birinchi yig'adi, pauza maqsadi sozlanadi (MaxGCPauseMillis), ko'p ish concurrent, lekin evacuation STW. ZGC (15+ production): deyarli hamma ish concurrent, pauza <1ms heap hajmidan qat'i nazar (TB gacha), colored pointers, lekin CPU/throughput ~10% ko'proq. Kechikish kritik (to'lov API) va heap katta → ZGC; umumiy holat → G1.
?Stack va heap farqi? StackOverflowError qachon?
Stack — har thread'ga alohida, LIFO freymlar, lokal primitivlar va havolalar, metod tugashi bilan avtomatik bo'shaydi, GC kerak emas. Heap — barcha thread'larga umumiy, obyektlar, GC boshqaradi. StackOverflowError — chuqur/cheksiz rekursiya (stek ~1MB tugadi). OOM — heap tugadi.
?String pool va intern()?
String literallari heap'dagi maxsus pool'da saqlanadi — bir xil literal bitta obyekt. new String("a") pool'dan tashqarida yangi obyekt. intern() pool'dagi nusxani qaytaradi. Ko'p takrorlanadigan string (valyuta kodi) uchun xotira tejaydi; G1'da -XX:+UseStringDeduplication avtomatik.
?Konteynerda JVM xotirasini qanday sozlaysiz?
Konteyner limitini JVM 10+ ko'radi. -XX:MaxRAMPercentage=75 (heap) — qolgan 25% Metaspace, thread stek, off-heap, GC uchun. Xms=Xmx qiling (resize pauzalarini oldini oladi). Actuator/Micrometer bilan jvm_memory_used va GC pauzalarni kuzating. OOM'da konteyner o'ladi (OOMKilled) — bu heap OOM'dan farq qiladi: JVM konteyner limitidan oshdi.
