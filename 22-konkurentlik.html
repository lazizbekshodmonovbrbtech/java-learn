Konkurentlik va thread'lar.

Server bir vaqtda minglab so'rovga xizmat qiladi — har biri o'z thread'ida. Ikki thread bitta hisobga tegsa nima bo'ladi? Bu modulda race condition'ni o'z ko'zingiz bilan ko'rasiz va uni to'g'ri yopishni o'rganasiz.

01

Hisob.java
// ❌ check-then-act — atomik emas
public void yech(long summa) {
    if (balans >= summa) {          // tekshirdi... shu orada boshqa thread yozib qo'ydi
        balans -= summa;
    }
}
// ✓ synchronized — bir vaqtda faqat bitta thread kiradi (monitor lock = this)
public synchronized void yech(long summa) { ... }

// ✓ Aniq lock — tryLock, timeout, fairness
private final ReentrantLock lock = new ReentrantLock();
public void yech(long summa) {
    lock.lock();
    try { if (balans >= summa) balans -= summa; }
    finally { lock.unlock(); }         // finally — exception bo'lsa ham bo'shatiladi
}
Suhbatda so'raladi
Bankda real yechim — bu Java lock emas, bazadagi lock: SELECT ... FOR UPDATE yoki optimistic @Version. Chunki server bir nechta instance bo'lsa, JVM ichidagi synchronized boshqa serverdagi thread'ni to'xtata olmaydi. Java lock — bitta JVM ichida; bazadagi lock — butun tizim uchun. (36-modulda chuqur.)
02

Thread hayot sikli

Thread — dastur ichidagi mustaqil bajarilish yo'li. Har bir thread o'z stek'iga ega, heap umumiy (shuning uchun balans umumiy edi). Holatni bosing.

NEWnew Thread()
RUNNABLEstart() → CPU
BLOCKEDlock kutmoqda
WAITINGwait/join/park
TERMINATEDrun() tugadi
Holatni tanlang. (TIMED_WAITING — sleep(ms), wait(ms) — muddatli kutish.)
Thread.java
Thread t = new Thread(() -> System.out.println("salom " + Thread.currentThread().getName()));
t.start();     // ✓ yangi thread'da ishlaydi
t.run();       // ❌ oddiy metod chaqiruvi — shu thread'da! (klassik suhbat savoli)
t.join();      // t tugaguncha kut
t.interrupt(); // "to'xta" belgisi — thread o'zi tekshirishi kerak (isInterrupted / InterruptedException)
// Amalda new Thread() yozmaysiz — ExecutorService ishlatasiz (pastda)
03

counter++ atomik emas

count++ aslida 3 ta amal: o'qi, 1 qo'sh, yoz. Ikki thread o'rtada aralashsa — bitta qo'shish yo'qoladi ("lost update"). 2 thread × 1000 marta:

Chapda natija har safar boshqacha va 2000 dan kam bo'ladi. O'ngda CAS (compare-and-swap) — protsessor darajasidagi atomik amal, lock'siz.

volatile — ko'rinish (visibility)

private volatile boolean stop;
// volatile'siz: thread o'z keshidagi
// eski qiymatni cheksiz o'qishi mumkin
while (!stop) { ... }
volatile: har o'qish/yozish asosiy xotiradan. Atomiklik bermaydi (count++ uchun yetmaydi), faqat ko'rinish + tartib (happens-before).

Atomic* — lock'siz atomiklik

AtomicLong seq = new AtomicLong();
seq.incrementAndGet();
seq.compareAndSet(kutilgan, yangi);
LongAdder — juda ko'p yozuvda tezroq
Bitta o'zgaruvchi uchun ideal. Bir nechta o'zgaruvchi birga o'zgarishi kerak bo'lsa — lock kerak.

Thread yaratish qimmat — pool'da qayta ishlatiladi. Mijoz sahifasi uchun 3 ta servisdan ma'lumot kerak: profil (300ms), hisoblar (500ms), kartalar (400ms). Ketma-ket vs parallel:

MijozSahifa.java
ExecutorService pool = Executors.newFixedThreadPool(8);   // yoki Spring'ning @Async

var profil   = CompletableFuture.supplyAsync(() -> profilSvc.ol(id), pool);
var hisoblar = CompletableFuture.supplyAsync(() -> hisobSvc.ol(id), pool);
var kartalar = CompletableFuture.supplyAsync(() -> kartaSvc.ol(id), pool);

Sahifa s = profil.thenCombine(hisoblar, (p, h) -> new Sahifa(p, h))
                 .thenCombine(kartalar, Sahifa::kartalarBilan)
                 .exceptionally(ex -> Sahifa.bosh())   // xato bo'lsa fallback
                 .orTimeout(2, TimeUnit.SECONDS)
                 .join();                              // natijani kut

// Future.get() — bloklaydi; CompletableFuture — zanjir: thenApply / thenAccept / thenCompose / allOf
Pool o'lchami
CPU-og'ir ish: yadro soni (+1). I/O-og'ir: ko'proq (yadro × (1 + kutish/ish)), yoki Java 21 virtual thread. newCachedThreadPool — chegarasiz, xavfli. Pool'ni shutdown() qiling, Spring'da ThreadPoolTaskExecutor bean sifatida.
05

Deadlock: ikki lock, ikki tartib

O'tkazma A→B hisob A'ni, keyin B'ni lock qiladi. Bir vaqtda B→A o'tkazma B'ni, keyin A'ni. Har biri o'zinikini olib, boshqasinikini kutadi — abadiy.

T1: A → B o'tkazma

lock(A)
lock(B)
o'tkaz, unlock
🔒 Hisob Abo'sh
🔒 Hisob Bbo'sh

T2: B → A o'tkazma

lock(B)
lock(A)
o'tkaz, unlock
☠ DEADLOCK — T1 B'ni kutadi (T2'da), T2 A'ni kutadi (T1'da). Ikkalasi ham abadiy BLOCKED.
Yechim: lock'larni doim bir xil tartibda oling (masalan, hisob ID bo'yicha kichigini birinchi). Yoki tryLock(timeout). Bazada ham xuddi shu: UPDATE'larni id tartibida bajaring.

07

Suhbat savollari

?Process va thread farqi?
Process — o'z xotirasiga ega alohida dastur (JVM — bitta process). Thread — process ichidagi bajarilish yo'li; thread'lar heap'ni bo'lishadi, har birining o'z stek'i va PC registri bor. Shuning uchun thread'lar orasida ma'lumot almashish oson, lekin race condition xavfi bor.
?Race condition nima? Qanday oldini olasiz?
Natija thread'larning bajarilish tartibiga bog'liq bo'lib qolishi (check-then-act, read-modify-write). Yechimlar: synchronized/ReentrantLock (o'zaro istisno), Atomic* (CAS), immutable obyektlar, thread-confinement (ThreadLocal), concurrent kolleksiyalar. Bank amaliyotida — baza darajasida: SELECT FOR UPDATE yoki optimistic locking (@Version).
?synchronized qanday ishlaydi? volatile bilan farqi?
Har obyektda monitor bor; synchronized blok/metod monitorni oladi, boshqa thread'lar BLOCKED bo'ladi; chiqishda bo'shatadi va o'zgarishlar ko'rinadigan bo'ladi (happens-before). volatile faqat ko'rinish va tartibni kafolatlaydi (kesh emas, asosiy xotira), atomiklik bermaydi — count++ uchun yetmaydi. Bayroq (flag) uchun volatile, murakkab holat uchun lock.
?start() va run() farqi?
start() yangi OS thread yaratib, unda run()ni chaqiradi. run()ni to'g'ridan-to'g'ri chaqirsangiz — oddiy metod, joriy thread'da ishlaydi, parallellik yo'q. start()ni ikki marta chaqirish — IllegalThreadStateException.
?Deadlock nima, qanday oldini olasiz?
Ikki+ thread bir-birining lock'ini siklik kutishi. 4 shart: mutual exclusion, hold-and-wait, no preemption, circular wait. Oldini olish: lock'larni global tartibda olish (circular wait'ni sindiradi), tryLock(timeout), bitta lock ostida ishlash, lock hold vaqtini qisqartirish. Aniqlash: jstack thread dump 'Found one Java-level deadlock'.
?ExecutorService nima uchun? Thread pool o'lchami?
Thread yaratish/yo'q qilish qimmat; pool thread'larni qayta ishlatadi va navbatni boshqaradi. FixedThreadPool (chegarali), CachedThreadPool (chegarasiz — xavfli), ScheduledThreadPool, virtual (21). O'lcham: CPU-bound → yadro soni; I/O-bound → yadro × (1 + kutish/hisob vaqti). Har doim shutdown() / try-with-resources (21).
?CompletableFuture va Future farqi?
Future — faqat get() (bloklaydi) va isDone(). CompletableFuture — zanjir (thenApply/thenCompose/thenCombine), xato boshqaruvi (exceptionally/handle), allOf/anyOf, timeout, manual complete(). Non-blocking kompozitsiya — bir nechta servisni parallel chaqirib birlashtirish.
?ConcurrentHashMap qanday ishlaydi? HashMap'dan farqi?
HashMap thread-safe emas — parallel put'da ma'lumot yo'qolishi, hatto cheksiz sikl (Java 7) bo'lishi mumkin. ConcurrentHashMap: bucket darajasida lock (Java 8: CAS + synchronized per bin), o'qish lock'siz, iterator weakly-consistent (CME tashlamaydi). null kalit/qiymatga ruxsat yo'q. compute/merge atomik.
?ThreadLocal nima, qayerda xavfli?
Har thread uchun alohida qiymat (Map kabi). Spring Security'da SecurityContextHolder, tranzaksiya konteksti, MDC log. Xavf: thread pool'da thread qayta ishlatiladi — remove() qilinmasa eski foydalanuvchi ma'lumoti keyingi so'rovga 'o'tib' qoladi (leak + xavfsizlik). finally'da remove().
?wait/notify va sleep farqi?
sleep — thread muddat kutadi, lock'ni QO'YMAYDI, Thread'ning static metodi. wait — monitor lock'ni bo'shatib, notify/notifyAll'ni kutadi, faqat synchronized ichida chaqiriladi, Object metodi. Zamonaviy kodda wait/notify o'rniga BlockingQueue, CountDownLatch, Condition ishlatiladi.
