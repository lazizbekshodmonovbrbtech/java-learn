REST API chuqur

Mobil ilova POST /transfers yubordi. Tomcat'dan controller'gacha nima bo'ladi? Qaysi status kod? Ikki marta bosilsa pul ikki marta ketadimi? Bu modul — REST'ni bank darajasida.

01

So'rov sayohati: Tomcat → Controller → Baza → JSON

POST /api/v1/transfers so'rovi 14 bosqichdan o'tadi. Ko'p suhbat savoli shu yerda: Filter va Interceptor farqi, DispatcherServlet nima qiladi, JSON qayerda obyektga aylanadi.

TransferController.java
@RestController
@RequestMapping("/api/v1/transfers")
@RequiredArgsConstructor
class TransferController {
    private final TransferService service;

    @PostMapping
    ResponseEntity<TransferResponse> create(@Valid @RequestBody TransferRequest req,
                                             @RequestHeader("Idempotency-Key") String key) {
        TransferResponse r = service.transfer(req, key);
        return ResponseEntity.created(URI.create("/api/v1/transfers/" + r.id())).body(r);  // 201 + Location
    }

    @GetMapping("/{id}")
    TransferResponse get(@PathVariable UUID id) { return service.get(id); }   // 200, JSON avtomatik

    @GetMapping
    Page<TransferResponse> list(@RequestParam(defaultValue = "0") int page,
                                @RequestParam(defaultValue = "20") int size) {
        return service.list(PageRequest.of(page, Math.min(size, 100)));   // chegara!
    }
}

@Transactional
TransferResponse transfer(TransferRequest req, String key) {
    return idemRepo.findByKey(key)                  // avval ko'rilganmi?
        .map(IdempotencyRecord::response)              // ha → o'sha javobni qaytar, qayta bajarma

06
Suhbat savollari

    
?REST nima? RESTful API tamoyillari?
Representational State Transfer — resurslar (URL bilan identifikatsiya), standart HTTP metodlari (GET/POST/PUT/PATCH/DELETE), stateless (har so'rov mustaqil, sessiya serverda saqlanmaydi), vakillik (JSON), status kodlar, keshlanuvchanlik, bir xil interfeys. HATEOAS — javobda keyingi amallar linklari (amalda kam ishlatiladi).


?Filter va Interceptor farqi?
Filter — Servlet spec, DispatcherServlet'dan OLDIN, Spring kontekstidan mustaqil (lekin bean bo'lishi mumkin), request/response'ni o'rashi/o'zgartirishi mumkin, Security shu yerda. HandlerInterceptor — Spring MVC, handler (controller metodi) ma'lum, preHandle/postHandle/afterCompletion, ModelAndView ko'radi, body'ga tegmaydi. AOP (@Aspect) — metod darajasida, HTTP'dan bexabar.


?DispatcherServlet nima qiladi?
Front Controller: hamma HTTP so'rov unga keladi. HandlerMapping'dan handler topadi → HandlerAdapter orqali chaqiradi (argument resolver'lar, @Valid) → qaytgan qiymatni HttpMessageConverter (Jackson) bilan body'ga yozadi yoki ViewResolver'ga beradi → exception bo'lsa HandlerExceptionResolver (@ControllerAdvice).


?PUT va PATCH farqi? POST va PUT?
PUT — resursni to'liq almashtirish, idempotent, mijoz to'liq holat yuboradi. PATCH — qisman yangilash (faqat o'zgargan maydonlar; JSON Merge Patch / JSON Patch), idempotent bo'lishi shart emas. POST — yangi resurs yaratish yoki 'amal' (server ID beradi), idempotent emas. PUT /users/5 — ID mijozda; POST /users — ID server beradi.


?Idempotentlik nima, POST'ni qanday idempotent qilasiz?
Bir xil so'rovni N marta bajarish natijasi 1 marta bajarishga teng. GET/HEAD/PUT/DELETE idempotent, POST/PATCH — yo'q. Yechim: mijoz Idempotency-Key (UUID) header yuboradi, server kalit+javobni saqlaydi (UNIQUE constraint, TTL), takror kelsa saqlangan javobni qaytaradi; bir xil kalit boshqa body → 422. To'lovlarda majburiy.


?401 va 403 farqi? 400 va 422?
401 — autentifikatsiya yo'q/noto'g'ri (kim ekaningiz noma'lum), 403 — autentifikatsiya bor, lekin ruxsat yo'q. 400 — sintaktik xato (JSON buzuq, tip mos emas), 422 — sintaksis to'g'ri, semantika/biznes qoida buzilgan (balans yetmaydi). Ko'p jamoalar validatsiyaga 400, biznesga 422 ishlatadi — muhimi izchillik.


?Nega Entity'ni to'g'ridan-to'g'ri qaytarmaslik kerak?
Ichki maydonlar (parol hash, ichki ID) sizadi; API kontrakt baza sxemasiga bog'lanib qoladi (ustun o'zgarsa mijozlar sinadi); lazy bog'lanishlar serializatsiyada LazyInitializationException yoki cheksiz rekursiya (bidirectional); ortiqcha ma'lumot. DTO/record + MapStruct.


?Stateless nima uchun muhim? Sessiya qayerda?
Server so'rovlar orasida mijoz holatini saqlamaydi — har so'rov o'zi bilan hamma kerakli narsani (JWT) olib keladi. Foyda: gorizontal masshtab (istalgan instance javob beradi), sticky session kerak emas, restart bexavf. Holat kerak bo'lsa — baza/Redis'da, server xotirasida emas.


?API versiyalash usullari?
URL (/api/v1/...) — eng ko'p, oddiy, kesh/log'da ko'rinadi. Header (Accept: application/vnd.bank.v2+json) — 'toza' REST, lekin sinash qiyin. Query (?version=2) — kam. Qoida: buzuvchi o'zgarishda yangi versiya, qo'shimcha maydon — versiyasiz (mijoz noma'lum maydonni e'tiborsiz qoldirishi kerak — Jackson default).


?Katta ro'yxatni qanday qaytarasiz?
Sahifalash majburiy: ?page=0&size=20 (size chegarasi, masalan 100), Spring Data Page (content, totalElements, totalPages) yoki keyset/cursor pagination (?after=id — katta jadvalda OFFSET sekin). Sort parametr, filtrlar. Hech qachon findAll() ni ochiq qoldirmang.
