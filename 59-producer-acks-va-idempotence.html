03

Retry, dublikat va idempotent producer

Tarmoq tasodifan ack’ni yo‘qotdi (xabar yozilgan, lekin producer bilmaydi). Producer qayta yuboradi. Nima bo‘ladi?

💡 Idempotent producer qanday ishlaydi
Broker har producer’ga PID beradi, producer har partition uchun har batch’ga ketma-ket sequence number qo‘yadi. Broker oxirgi 5 ta batch’ning seq’ini eslab qoladi: takror kelsa — yozmaydi, lekin ack qaytaradi; oraliq bo‘lsa — OutOfOrderSequence. Shuning uchun max.in.flight.requests.per.connection ≤ 5 bilan ham tartib saqlanadi. Kafka 3.0+ da default yoqilgan. Diqqat: bu faqat bitta producer sessiyasi ichidagi retry’dan himoya — ilova o‘zi qayta yuborsa (restart), dublikat bo‘ladi → biznes kaliti bilan idempotent consumer (63-modul).

PaymentEventPublisher.java
@Service
@RequiredArgsConstructor
class PaymentEventPublisher {
    private final KafkaTemplate<String, PaymentEvent> kafka;

    void published(Payment p) {
        var ev = new PaymentEvent(p.id(), p.accountNo(), p.amount(), Instant.now());
        kafka.send("tolovlar", p.accountNo(), ev)             // kalit = hisob raqami → tartib
             .whenComplete((res, ex) -> {
                 if (ex != null) log.error("Yuborilmadi: {}", p.id(), ex);    // alert + Outbox'ga qaytish
                 else log.debug("offset {}", res.getRecordMetadata().offset());
             });
    }
}
// ❌ kafka.send(...).get() har xabarda — sinxron, batching yo'qoladi, throughput 10-100x tushadi
⚠️ DB tranzaksiyasi + send = dual write
To‘lovni DB’ga commit qilib, keyin Kafka’ga yuborsangiz: commit bo‘ldi, send muvaffaqiyatsiz → hodisa yo‘q. Teskarisi: send bo‘ldi, commit rollback → soxta hodisa. Ishonchli yechim — Transactional Outbox (63-modul).
06

Suhbat savollari

?acks=0/1/all farqi va bankda qaysi?›
0 — javob kutilmaydi; 1 — leader yozdi; all — barcha ISR yozdi. Bankda acks=all + min.insync.replicas=2 + RF=3: bitta broker yo‘qolsa ham ma’lumot yo‘qolmaydi va yozish davom etadi.
?Idempotent producer nima va qanday ishlaydi?›
Retry tufayli dublikat va tartib buzilishining oldini oladi: PID + har partition uchun sequence number, broker takrorni tashlaydi. Kafka 3.0+ da default. Faqat bitta producer instance ichida ishlaydi.
?Producer’da tartib qachon buzilishi mumkin?›
Idempotence o‘chiq va max.in.flight > 1 bo‘lsa: 1-batch xato qaytaradi, 2-batch yoziladi, 1-batch retry’da keyin yoziladi. Yechim: idempotence yoqish (≤5 in-flight bilan ham tartib saqlanadi).
?linger.ms va batch.size nima uchun?›
Throughput va kechikish muvozanati: xabarlarni yig‘ib bitta so‘rovda yuborish tarmoq va diskni tejaydi, siqishni samarali qiladi; evaziga har xabar linger.ms gacha kutishi mumkin.
?send() qaytgan Future’ni get() qilish kerakmi?›
Odatda yo‘q — callback/whenComplete ishlating. Har xabarda get() producer’ni sinxron qiladi va batching’ni yo‘q qiladi. Faqat juda kam hollarda (masalan, test yoki kritik bitta xabar) ishlatiladi.
?Xabar yuborilmasa nima qilasiz?›
delivery.timeout.ms ichida producer o‘zi retry qiladi; baribir xato bo‘lsa — callback’da log/alert va qayta yuborish strategiyasi. Eng ishonchli — Outbox: hodisa DB tranzaksiyasi ichida outbox jadvaliga yoziladi, alohida jarayon Kafka’ga uzatadi.
