Keshlash pattern’lari

"Keshni qo‘shdik — tezlashdi" — bu hikoyaning faqat boshi. Kesh ikkita yangi muammo olib keladi: eskirgan ma’lumot va kesh bo‘shaganda DB’ga tushadigan to‘lqin. Bu modulda pattern’larni ketma-ketlik diagrammalarida, poyga holatini vaqt chizig‘ida, uch klassik muammoni esa jonli simulyatorda ko‘ramiz.

02

Poyga holati: nega kesh eskirib qoladi?

Cache-aside + "yozishda DEL" ham 100% kafolat bermaydi. Ikki ip: A — o‘qiydi, B — yangilaydi. Qadamlarni kuzating.

🧵 A ip (o‘qish: GET /kurs)
🧵 B ip (admin kursni o‘zgartiradi)
PostgreSQL12 650
Redis—

Yechimlar

1) Har doim TTL — eskirish vaqt bilan chegaralanadi. 2) Delayed double delete: DEL → yozish → 500 ms keyin yana DEL. 3) CDC: Debezium PG WAL’ni o‘qib, o‘zgarishda keshni o‘chiradi (Kafka orqali). 4) Versiya: qiymat bilan version saqlash, eskisi yangisini bosmasin (Lua).

Qilmang

Yozishda SET cache (DEL o‘rniga): ikki parallel yozuvchi DB’ni bir tartibda, keshni boshqa tartibda yangilasa — kesh abadiy noto‘g‘ri (TTL tugaguncha). Avval keshni, keyin DB’ni yangilash: DB tranzaksiyasi rollback bo‘lsa, kesh yolg‘on gapiradi.

04

Spring Boot: @Cacheable + Redis

Spring Cache abstraksiyasi — cache-aside’ni annotatsiya bilan. Konfiguratsiya va eng ko‘p uchraydigan tuzoqlar.

build.gradle / application.yml
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.springframework.boot:spring-boot-starter-cache'

spring:
  data.redis:
    host: redis.bank.local
    port: 6379
    timeout: 200ms          # Redis sekinlashsa — tez voz kechamiz
  cache:
    type: redis
CacheConfig.java
@Configuration
@EnableCaching
class CacheConfig {
    @Bean
    RedisCacheManagerBuilderCustomizer caches() {
        var json = RedisSerializationContext.SerializationPair
            .fromSerializer(new GenericJackson2JsonRedisSerializer());   // JDK serializatsiya emas!
        var base = RedisCacheConfiguration.defaultCacheConfig()
            .serializeValuesWith(json)
            .prefixCacheNameWith("bank:v1:")           // versiya — DTO o'zgarsa v2
            .disableCachingNullValues();
        return b -> b
            .withCacheConfiguration("kurslar",  base.entryTtl(Duration.ofSeconds(60)))
            .withCacheConfiguration("mijozlar", base.entryTtl(Duration.ofMinutes(10)));
    }
}
KursService.java
@Service
class KursService {
    @Cacheable(cacheNames = "kurslar", key = "#valyuta", sync = true)   // sync: bitta JVM ichida single-flight
    public KursDto kurs(String valyuta) {
        return repo.findLatest(valyuta);                                   // faqat miss bo'lganda chaqiriladi
    }

    @CacheEvict(cacheNames = "kurslar", key = "#dto.valyuta()")          // DB'dan KEYIN o'chiradi
    @Transactional
    public void yangilash(KursDto dto) { repo.save(dto.toEntity()); }
}

Tuzoq 1: self-invocation

Xuddi @Transactional kabi: this.kurs("USD") proxy’dan o‘tmaydi — kesh ishlamaydi. Boshqa bean orqali chaqiring.

Tuzoq 2: sync=true — faqat bitta JVM

10 pod bo‘lsa, har pod bittadan — 10 ta so‘rov DB’ga. Klaster bo‘ylab single-flight uchun Redis lock (54-modul) yoki SWR kerak.

Tuzoq 3: @CacheEvict + tranzaksiya

Evict metod tugagach ishlaydi, lekin commit undan keyin bo‘lishi mumkin — oraliqda boshqa ip eski qiymatni qayta keshlaydi. Ishonchli: TransactionSynchronization.afterCommit yoki @TransactionalEventListener(phase = AFTER_COMMIT)da o‘chirish.

Tuzoq 4: serializatsiya

JDK serializatsiya — o‘qib bo‘lmaydi, klass o‘zgarsa buziladi, xavfsizlik riski. JSON + kesh prefiksida versiya. DTO’ni keshlang, JPA entity’ni emas (lazy proxy!).

06

Suhbat savollari

?Cache-aside pattern’ni tushuntiring. Yozishda nega keshni yangilash emas, o‘chirish kerak?›
O‘qish: keshdan, bo‘lmasa DB’dan o‘qib keshga TTL bilan yozish. Yozish: avval DB, keyin keshdan DEL. SET qilsak, ikki parallel yozuvchi DB va keshni turli tartibda yangilab, keshda eski qiymat qolishi mumkin; bundan tashqari, hech kim o‘qimaydigan qiymatni hisoblashga vaqt ketadi. DEL — keyingi o‘quvchi yangi qiymatni yuklaydi.
?DB’dan keyin DEL qilsak ham eskirgan qiymat qolishi mumkinmi?›
Ha: A miss bo‘lib DB’dan eski qiymatni o‘qidi, shu payt B DB’ni yangilab DEL qildi, keyin A eski qiymatni SET qildi. Ehtimoli past (o‘qish odatda yozishdan tez), lekin bor. Yumshatish: TTL, delayed double delete, CDC orqali invalidatsiya, versiyalash.
?Cache stampede nima va qanday oldini olasiz?›
Issiq kalit o‘lganda parallel so‘rovlar birdaniga DB’ga boradi. Yechimlar: mutex/single-flight (SET lock NX, faqat bittasi yuklaydi, qolganlari kutadi yoki eski qiymat oladi), stale-while-revalidate (logik muddat: eski qiymat qaytariladi, fonda yangilanadi), refresh-ahead, ehtimoliy erta yangilash (XFetch).
?Cache penetration va Bloom filter?›
Mavjud bo‘lmagan kalitlar so‘rovi keshda hech qachon topilmaydi va har doim DB’ga tushadi. Takrorlanuvchi ID’lar uchun null’ni qisqa TTL bilan keshlash yetadi; tasodifiy ID’lar hujumida — Bloom filter (mavjud ID’lar to‘plami, "yo‘q" javobi 100% aniq, "bor" — ehtimoliy), plus validatsiya va rate limit.
?Cache avalanche va farqi?›
Ko‘p kalit bir vaqtda muddati tugaydi yoki Redis butunlay ishdan chiqadi — trafik to‘lqini DB’ga. Stampede — bitta issiq kalit, avalanche — ommaviy. Yechim: TTL jitter, HA Redis, circuit breaker + lokal kesh, DB oldida rate limit/bulkhead, warm-up.
?@Cacheable(sync = true) nima qiladi va cheklovi?›
Bitta kesh kaliti uchun bir vaqtda faqat bitta ip metodni chaqiradi, qolganlari natijani kutadi — lekin faqat bitta JVM ichida. Ko‘p pod’li tizimda har pod o‘z yuklashini qiladi.
?Keshdagi ma’lumot bilan DB mos kelmasligini qancha vaqt qabul qila olasiz? Bu kimning qarori?›
Bu biznes qarori: kurs uchun 60 s normal, balans uchun — 0 (keshlanmaydi yoki faqat ko‘rsatish uchun va pul operatsiyasi oldidan DB’dan tekshiriladi). TTL shu toqat chegarasiga qarab tanlanadi.
