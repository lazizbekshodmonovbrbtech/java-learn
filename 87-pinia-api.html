Pinia va API qatlami: holat, token, xatolar

Balans sarlavhada, kartalar sahifasida va o‘tkazma formasida ko‘rinadi. Props bilan uzatish — azob. Pinia — global, reaktiv, devtools’da kuzatiladigan do‘kon (store). Unga axios qatlami qo‘shiladi: har so‘rovga token qo‘yadi, 401 bo‘lsa tokenni yangilaydi va xatolarni bir joyda boshqaradi. Eng qiziq joyi — 5 ta so‘rov bir vaqtda 401 olganda nima bo‘ladi.

01

Store: bitta manba, ko‘p o‘quvchi + optimistic update

stores/hisob.ts (setup store)
export const useHisobStore = defineStore('hisob', () => {
  const balans = ref(0)
  const tarix = ref<Amal[]>([])
  const limit = computed(() => Math.min(balans.value, 5_000_000))   // getter

  async function otkazmaQil(summa: number, kimga: string) {           // action
    const oldin = balans.value
    balans.value -= summa                         // ⚡ optimistic
    const vaqtincha = { id: crypto.randomUUID(), summa, kimga, holat: 'kutilmoqda' }
    tarix.value.unshift(vaqtincha)
    try {
      const res = await api.post('/transfers', { summa, kimga },
        { headers: { 'Idempotency-Key': vaqtincha.id } })
      Object.assign(vaqtincha, res.data)          // server tasdig'i
    } catch (e) {
      balans.value = oldin                         // ↩ rollback
      tarix.value = tarix.value.filter(a => a !== vaqtincha)
      throw e
    }
  }
  return { balans, tarix, limit, otkazmaQil }
})

02

5 ta so‘rov, 1 ta eskirgan token

Dashboard ochildi: 5 ta widget bir vaqtda API’ga so‘rov yubordi. Access token 1 soniya oldin tugagan. Keycloak refresh token rotation yoqilgan — har refresh token faqat bir marta ishlatiladi. Ikkala interceptor’ni solishtiring.

Tugmalardan birini bosing.
api/http.ts — single-flight refresh
export const api = axios.create({ baseURL: '/api', timeout: 15_000 })

api.interceptors.request.use(cfg => {
  cfg.headers.Authorization = `Bearer ${keycloak.token}`
  return cfg
})

let refreshing: Promise<boolean> | null = null      // ← bitta umumiy va'da

api.interceptors.response.use(r => r, async (err) => {
  const cfg = err.config
  if (err.response?.status !== 401 || cfg._retry) return Promise.reject(err)
  cfg._retry = true
  refreshing ??= keycloak.updateToken(-1)          // birinchisi boshlaydi, qolganlari kutadi
    .finally(() => { refreshing = null })
  try {
    await refreshing
  } catch {
    keycloak.login()                                // refresh ham o'tmadi → qayta login
    return Promise.reject(err)
  }
  cfg.headers.Authorization = `Bearer ${keycloak.token}`
  return api(cfg)                                   // so'rovni qaytadan yuborish
})
Markaziy xato boshqaruvi
Response interceptor’da: 401 → refresh; 403 → "ruxsat yo‘q" toast; 409/422 → forma xatolari (backend ProblemDetail, 25-modul); 5xx/tarmoq → "qayta urinib ko‘ring" va Sentry’ga log. Komponentlar faqat o‘z holatini bilsin — texnik xatolar bitta joyda.
03

Suhbat savollari

?Pinia nima uchun kerak? Vuex’dan farqi?›
Global holat uchun rasmiy kutubxona: state, getters, actions; devtools (time-travel, action log), SSR va HMR qo‘llovi. Vuex’dan farqi: mutations yo‘q (action’da to‘g‘ridan o‘zgartirish), to‘liq TypeScript tip chiqarish, modullar o‘rniga bir nechta mustaqil store, setup store (Composition API uslubida).
?storeToRefs nima uchun kerak?›
Store reactive obyekt — undan destructuring qilinsa state/getters reaktivligini yo‘qotadi. storeToRefs ularni ref’larga aylantiradi. Action’lar esa oddiy funksiya — ularni to‘g‘ridan destructure qilish mumkin.
?Optimistic update nima va bankda qachon ishlatish mumkin?›
UI server javobini kutmasdan o‘zgaradi, xato bo‘lsa rollback. Tezkor his beradi. Bankda — ehtiyotkorlik bilan: "kutilmoqda" holatini ko‘rsatish, idempotency key bilan qayta yuborishdan himoya, yakuniy balansni baribir serverdan olish. Katta summali yoki qaytarib bo‘lmaydigan amallar uchun pessimistic (spinner + tasdiq) afzal.
?Bir vaqtda bir necha so‘rov 401 olsa token refresh qanday bo‘ladi?›
Single-flight: birinchi 401 refresh’ni boshlaydi va promise’ni umumiy o‘zgaruvchida saqlaydi, qolganlari shu promise’ni kutadi, keyin hammasi yangi token bilan qayta yuboriladi. Aks holda refresh token rotation’da ikkinchi refresh invalid_grant oladi va foydalanuvchi tasodifan logout bo‘ladi.
?Token’ni qayerda saqlash kerak — localStorage’dami?›
keycloak-js tokenni xotirada (JS o‘zgaruvchida) saqlaydi — XSS’da localStorage’dan o‘g‘irlash osonroq. Eng xavfsiz variant — BFF (backend-for-frontend) pattern: token server tomonda, brauzerda faqat HttpOnly, Secure, SameSite cookie.
?Pinia va composable farqi?›
Composable har chaqiruvda yangi holat yaratadi (agar holat funksiya ichida bo‘lsa) — komponentga lokal. Pinia store — ilova bo‘ylab yagona instansiya (singleton), devtools, plugin (persist), SSR. Umumiy holat kerak bo‘lsa — store; qayta ishlatiladigan mantiq — composable.
