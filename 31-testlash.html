Mockito: bog'liqlikni "soxtalashtirish"

TransferService'ni test qilamiz — bazasiz. Repository o'rniga mock: "findById(1) chaqirilsa, shu hisobni qaytar". Mock xatti-harakatini tanlang va testni ishga tushiring:

Mock sozlamasi (Arrange)
Test kodi
// Arrange — mock va servis TransferRepository repo = mock(...); var svc = new TransferService(repo, clock); // Act svc.transfer(1L, 2L, of(300)); // Assert verify(repo).save(argThat(t -> t.amount().equals(of(300)))); assertThat(hisob.balance()).isEqualByComparingTo("700");
Natija shu yerda
Mock — real klass o'rniga "yozib olingan javoblar". Baza, tarmoq, vaqt — hammasi soxta, test 5 ms.
TransferServiceTest.java
@ExtendWith(MockitoExtension.class)              // Spring YO'Q — sof unit test
class TransferServiceTest {
    @Mock TransferRepository repo;
    @Mock AccountRepository accRepo;
    @InjectMocks TransferService svc;                   // konstruktor orqali mock'lar beriladi

    @Test void balansYetmasa_exception_vaSaqlanmaydi() {
        // given
        var a = new Account(1L, new BigDecimal("100"));
        when(accRepo.findByIdForUpdate(1L)).thenReturn(Optional.of(a));
        // when / then
        assertThatThrownBy(() -> svc.transfer(1L, 2L, new BigDecimal("300")))
            .isInstanceOf(InsufficientFundsException.class)
            .hasMessageContaining("100");
        verify(repo, never()).save(any());                 // hech narsa saqlanmadi
        verifyNoMoreInteractions(repo);
    }

    @ParameterizedTest @CsvSource({"1000, 300, 700", "300, 300, 0"})
    void debit(BigDecimal bal, BigDecimal amt, BigDecimal kutilgan) { ... }
}
Test dubllari lug'ati
Dummy — faqat parametrni to'ldirish. Stub — tayyor javob qaytaradi (when/thenReturn). Mock — stub + chaqiruvlarni tekshirish (verify). Spy — real obyekt, ba'zi metodlari o'zgartirilgan. Fake — soddalashtirilgan ishlaydigan implementatsiya (InMemoryRepo). Mockito mock/spy beradi. Qoida: o'zingizniki bo'lmagan narsani mock qilmang (RestClient'ni emas — uni o'ragan adapter'ingizni).

Slice testlar: konteynerning bir bo'lagi

@SpringBootTest butun ilovani ko'taradi (sekin). Slice — faqat kerakli qatlam. Annotatsiyani tanlang — qaysi bean'lar yuklanishini ko'ring:

Slice misollari
@WebMvcTest(TransferController.class)              // faqat MVC: controller, advice, filter, Jackson
class TransferControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean TransferService service;          // Boot 3.4+ (@MockBean eskirgan)

    @Test void manfiySumma_400() throws Exception {
        mvc.perform(post("/api/v1/transfers").contentType(APPLICATION_JSON)
                .content("""{"fromAccount":"2020...","toAccount":"2020...","amount":-5,"currency":"UZS"}"""))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.errors[0].field").value("amount"));
        verifyNoInteractions(service);                  // validatsiya servisgacha qo'ymadi
    }
}

@DataJpaTest                                          // faqat JPA: entity, repository, tx (har test rollback)
@AutoConfigureTestDatabase(replace = NONE)           // H2 emas — real Postgres (Testcontainers)
class TransferRepositoryTest {
    @Autowired TransferRepository repo;
    @Autowired TestEntityManager em;
    @Test void derivedQuery_toGriIshlaydi() {
        em.persistAndFlush(transfer(COMPLETED, 500)); em.persistAndFlush(transfer(PENDING, 900));
        assertThat(repo.findByStatusAndAmountGreaterThan(COMPLETED, ZERO)).hasSize(1);
    }
}

05

Suhbat savollari

?Unit, integration, e2e test farqi? Piramida nega?
Unit — bitta birlik (klass/metod), bog'liqliklar mock, ms'larda, Spring'siz. Integration — bir nechta komponent birga (Spring kontekst, real DB), sekundlar. E2E — butun tizim foydalanuvchi nuqtai nazaridan. Piramida: pastda ko'p tez arzon testlar (tez feedback, aniq lokalizatsiya), yuqorida kam sekin real testlar (ishonch). Teskari piramida (hammasi e2e) — sekin, mo'rt, xatoni topish qiyin.
?Mock va Stub farqi? Spy?
Stub — chaqiruvga tayyor javob (state verification: natijani tekshirasiz). Mock — qo'shimcha o'zaro ta'sirni tekshirish (behavior verification: verify(repo).save(...)). Mockito'da bitta obyekt ikkalasini qiladi. Spy — real obyekt, kerakli metodlari override (doReturn().when(spy)). Stub'ni ko'proq, verify'ni faqat muhim yon ta'sirlar (yuborildi/saqlandi) uchun ishlating — aks holda test implementatsiyaga yopishib qoladi.
?@Mock, @MockBean/@MockitoBean, @InjectMocks farqi?
@Mock — Mockito, Spring'siz, MockitoExtension bilan. @InjectMocks — test qilinayotgan klassni yaratib, @Mock'larni konstruktor/setter/maydon orqali beradi. @MockBean (Boot 3.4'dan @MockitoBean) — Spring kontekstidagi bean'ni mock bilan almashtiradi (slice/integration testlarda); har xil @MockBean to'plami — yangi kontekst (kesh buziladi, sekin).
?@WebMvcTest va @SpringBootTest farqi?
@WebMvcTest — faqat MVC infratuzilma + ko'rsatilgan controller(lar), advice, filter, Jackson, validatsiya; servislar yo'q (mock qilinadi); MockMvc — real server yo'q. @SpringBootTest — to'liq kontekst, ixtiyoriy real server (RANDOM_PORT + TestRestTemplate/WebTestClient), real bazaga ulanishi mumkin. Birinchisi kontrakt/validatsiya, ikkinchisi oqimlar uchun.
?Nega H2 o'rniga Testcontainers?
H2 Postgres'ni taqlid qiladi, lekin farqlar bor: jsonb, array, window/CTE nozikliklari, ON CONFLICT, lock semantikasi, tip konvertatsiyasi, migratsiya SQL sintaksisi. Testda o'tib prod'da yiqilish xavfi. Testcontainers Docker'da real Postgres (aynan prod versiyasi) ko'taradi; @ServiceConnection bilan sozlash avtomatik; static konteyner — hamma testga bitta.
?Flaky test nima, sabablari?
Kod o'zgarmasa ham goh o'tib goh yiqiladigan test. Sabablar: vaqt (Thread.sleep, real Clock, timeout), tartibga bog'liqlik (umumiy static holat, baza tozalanmagan), parallellik (race), tashqi servis/tarmoq, tasodifiy ma'lumot, xotira/resurs. Yechim: Clock inject, Awaitility (sleep o'rniga), har test mustaqil ma'lumot, mock tashqi servis, deterministik seed.
?Testda tranzaksiya qanday ishlaydi, tuzoqlari?
@DataJpaTest va @Transactional test — metod oxirida rollback. Tuzoq 1: flush bo'lmasa INSERT umuman ketmaydi — constraint xatolari ko'rinmaydi (saveAndFlush / em.flush). Tuzoq 2: LAZY yuklash testda ishlaydi (sessiya ochiq) — prod'da LazyInitializationException. Tuzoq 3: REQUIRES_NEW ichki tx test rollback'iga bo'ysunmaydi — baza ifloslanadi. @SpringBootTest + real HTTP'da test tx server thread'iga ta'sir qilmaydi — qo'lda tozalash (@Sql, truncate).
?Coverage 100% bo'lsa kod to'g'rimi?
Yo'q. Coverage — qaysi qatorlar bajarilgani, to'g'riligini tekshirilgani emas (assert'siz test ham coverage beradi). Muhimi: biznes qoidalar, chegara holatlar (0, manfiy, null, maksimal), xato yo'llari qamrovi. Mutation testing (PIT) — testlar xatoni sezadimi. 70–80% ma'noli coverage + kritik yo'llar 100% — real maqsad.
?Tashqi API'ni (masalan, boshqa bank) testda qanday almashtirasiz?
Unit'da — adapter interfeysini mock. Integration'da — WireMock/MockServer (HTTP darajasida stub: javob, kechikish, xato kodlari) yoki Testcontainers'da mock server. Kontrakt testlar (Pact, Spring Cloud Contract) — provayder va iste'molchi kelishuvi. Real API'ga test hech qachon urmasin.
