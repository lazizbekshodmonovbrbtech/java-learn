Kengaytirish va production

Dev'da Keycloak bir buyruq bilan ishga tushadi. Bankda esa undan ko'proq narsa talab qilinadi: MFA, brute-force himoyasi, korporativ AD, audit, klaster, uzilishsiz yangilash va regulyator tekshiruvi. Bu modul — o'sha "qolgan 90%".

01

Login oqimi konstruktori (Authentication flows)

Keycloak'da login — o'zgartiriladigan qadamlar daraxti. Har qadamning requirementi bor. OTP siyosatini tanlang, keyin foydalanuvchini tanlab, u qaysi yo'ldan o'tishini ko'ring.

💡 Step-up authentication
"Ko'rish uchun parol yetarli, o'tkazma uchun esa OTP kerak": Level of Authentication (LoA) sozlanadi. Ilova acr_values=2 (yoki claims) so'raydi, Keycloak kerak bo'lsa faqat OTP qadamini qo'shimcha so'raydi, tokendagi acr esa 2 bo'ladi. API o'tkazmada acr ≥ 2ni tekshiradi.
02

Brute-force himoyasi

Realm settings → Security defenses → Brute force detection. Hujumchi Otabekning parolini tanlamoqda. Tugmani bosib turing.

Max login failures: 5 · Wait increment: 1 daq · Max wait: 15 daq
Har urinish — LOGIN_ERROR hodisasi.
⚠ Ikki tomonlama qilich
Brute-force himoyasi boshqa odamni bloklab qo'yish uchun ham ishlatilishi mumkin: hujumchi ataylab noto'g'ri parol kiritib, haqiqiy mijozni kira olmaydigan qilib qo'yadi (DoS). Shuning uchun doimiy bloklash emas, vaqtinchalik (o'sib boruvchi) kutish. Qo'shimcha himoya — proksi/WAF darajasida IP bo'yicha rate limit va CAPTCHA.
03

Tashqi manbalar: brokering va federation

🌐 Identity brokering

Keycloak boshqa IdP'ga yo'naltiradi (Google, OneID, boshqa Keycloak, ADFS/SAML). U yerdan kelgan identity'ni o'z foydalanuvchisiga bog'laydi. First broker login flow: yangi user yaratish yoki mavjudiga bog'lash.

⚠ Email bo'yicha avtomatik bog'lash — faqat IdP email'ni tasdiqlagan bo'lsa (email_verified). Aks holda hujumchi sizning email'ingiz bilan akkaunt ochib, sizning akkauntingizga bog'lanib oladi.

🗂 User federation (LDAP / AD)

Xodimlar AD'da turadi. Keycloak LDAP'ga ulanadi: parolni AD'da tekshiradi, atributlar va guruhlarni mapper'lar bilan oladi. Rejimlar: READ_ONLY (AD — yagona manba), WRITABLE, UNSYNCED. Import yoqilsa, userlar Keycloak bazasiga ham nusxalanadi (tezroq, lekin sinxronizatsiya kerak).

Staff realm uchun odatiy tanlov: LDAP READ_ONLY + group mapper (AD guruhlari → Keycloak guruhlari → rollar).

05

Events, audit va kengaytirish (SPI)

Events

User events: LOGIN, LOGIN_ERROR, LOGOUT, CODE_TO_TOKEN, REFRESH_TOKEN, UPDATE_PASSWORD… Admin events: kim qaysi rolni kimga berdi (representation bilan). Bazada saqlanadi (expiration bilan) va event listener SPI orqali Kafka/SIEM'ga yuboriladi. Bank auditi uchun admin events majburiy.

SPI — kod bilan kengaytirish

Java JAR'ni /opt/keycloak/providers'ga qo'yasiz: Authenticator (masalan, SMS OTP yoki MyID), EventListener (Kafka), UserStorageProvider (eski bank bazasidagi foydalanuvchilar), ProtocolMapper (custom claim), RequiredAction. Theme — login sahifa dizayni (FreeMarker yoki Keycloakify/React).

Admin REST API — backend'dan foydalanuvchi yaratish
// org.keycloak:keycloak-admin-client — alohida client (service account + realm-management: manage-users)
Keycloak kc = KeycloakBuilder.builder().serverUrl("https://auth.bank.uz").realm("bank")
        .grantType("client_credentials").clientId("onboarding-service").clientSecret(secret).build();
UserRepresentation u = new UserRepresentation();
u.setUsername("998901234567"); u.setEnabled(true);
u.setAttributes(Map.of("mijoz_id", List.of("500123")));
u.setRequiredActions(List.of("UPDATE_PASSWORD", "CONFIGURE_TOTP"));
Response r = kc.realm("bank").users().create(u);        // 201 + Location: …/users/{id}

08

Suhbat savollari

?Keycloak'da MFA qanday yoqiladi? Faqat ba'zilarga-chi?›
Browser flow nusxasini olasiz (built-in flow'ni tahrirlamang), Forms ichidagi Conditional OTP sub-flow'ni CONDITIONAL qilasiz va condition qo'shasiz: "User configured" (OTP sozlaganlar), "User role" (masalan, KASSIR), yoki "Condition - client". OTP'ni majburiy qilish uchun Required action "Configure OTP"ni yoqasiz. WebAuthn/passkey — alohida authenticator. Flow'ni realm'ga (yoki bitta client'ga override qilib) bog'laysiz.
?Keycloak'ni qanday masshtablaysiz va HA qilasiz?›
Bir nechta stateless-ga yaqin nodalar LB orqasida, umumiy PostgreSQL (HA bilan), nodalar Infinispan orqali sessiya va keshlarni tarqatadi (26'da sessiyalar DB'da ham saqlanadi). Kubernetes'da Keycloak Operator, readiness/liveness :9000'da. Bottleneck ko'pincha DB va parol hashing (CPU — PBKDF2/Argon2 iteratsiyalari) bo'ladi.
?Identity brokering va user federation farqi?›
Brokering: autentifikatsiya boshqa IdP'da (foydalanuvchi o'sha yerga yo'naltiriladi, OIDC/SAML orqali). Federation: foydalanuvchi ma'lumotlari tashqi omborda (LDAP/AD), lekin login formasi Keycloak'niki, parolni Keycloak LDAP orqali tekshiradi.
?Keycloak'ni o'z ehtiyojimizga qanday moslaymiz?›
Avval konfiguratsiya (flow'lar, mapper'lar, policy'lar), keyin theme (dizayn), eng oxirida SPI (Java kodi). SPI kuchli, lekin har yangilashda qayta sinash kerak. Keycloak'ni fork qilmang.
?Keycloak xavfsizligi uchun eng muhim 5 ta sozlama?›
1) Admin konsol ichki tarmoqda / alohida hostname, master admin MFA bilan. 2) Aniq redirect URI'lar + PKCE S256, implicit va password grant o'chiq. 3) Qisqa access token, refresh rotation. 4) Brute-force + parol siyosati (+ MFA). 5) Events/admin events → SIEM, muntazam yangilash (CVE'lar).
