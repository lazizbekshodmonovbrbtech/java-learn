Pub/Sub, Streams va Spring

Redis xabar almashish uchun uch xil vosita beradi: Pub/Sub (radio — eshitmagan bo‘lsang, o‘tib ketdi), List (oddiy navbat) va Streams (jurnal + consumer group, Kafka’ning kichik ukasi). So‘ng Spring Data Redis’ni to‘liq sozlaymiz va Redis trekining yakuniy suhbat savollarini ko‘rib chiqamiz.

02

Streams: jurnal + consumer group

sms:outbox stream’i. notify guruhida ikki consumer. Xabar qo‘shing, consumer’lar o‘qisin, ack qilsin. Keyin C2’ni "o‘ldiring" va uning xabarlarini C1 ga XAUTOCLAIM bilan o‘tkazing.

XADD bilan boshlang. Yuqoridagi binafsha ko‘rsatkich — guruhning last-delivered-idsi.
redis-cli
XADD sms:outbox MAXLEN ~ 100000 * tel 998901234567 matn "Kod: 4821"
"1758612000000-0"                                  # ID = ms-vaqt-tartib raqami

XGROUP CREATE sms:outbox notify $ MKSTREAM          # $ — faqat yangi xabarlar
XREADGROUP GROUP notify c1 COUNT 10 BLOCK 5000 STREAMS sms:outbox >   # > — hali hech kimga berilmagan
XACK sms:outbox notify 1758612000000-0             # qayta ishlandi → PEL'dan chiqadi
XPENDING sms:outbox notify                          # kim nima olib, ack qilmagan
XAUTOCLAIM sms:outbox notify c1 60000 0-0 COUNT 10  # 60 s dan ortiq osilib qolganlarni c1 oladi
⚠️ Streams ≠ Kafka
Streams RAM’da — hajm cheklangan (MAXLEN bilan kesiladi). Replikatsiya asinxron — failover’da xabar yo‘qolishi mumkin. Partitsiyalash yo‘q (bitta kalit = bitta shard). Kichik va o‘rta oqimlar uchun ajoyib; bank hodisalar magistrali, uzoq saqlash va qayta o‘qish uchun — Kafka (keyingi trek).

RedisConfig.java
@Configuration
class RedisConfig {
    @Bean
    RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory cf, ObjectMapper om) {
        var t = new RedisTemplate<String, Object>();
        t.setConnectionFactory(cf);
        t.setKeySerializer(RedisSerializer.string());                   // kalitlar o'qiladigan
        t.setHashKeySerializer(RedisSerializer.string());
        t.setValueSerializer(new GenericJackson2JsonRedisSerializer(om)); // JDK emas!
        return t;
    }

    // Pub/Sub: kurs o'zgarsa lokal keshni tozalash
    @Bean
    RedisMessageListenerContainer listeners(RedisConnectionFactory cf, KursLocalCache cache) {
        var c = new RedisMessageListenerContainer();
        c.setConnectionFactory(cf);
        c.addMessageListener((msg, p) -> cache.evict(new String(msg.getBody())),
                             new ChannelTopic("kurs:yangilandi"));
        return c;
    }
}
SmsStreamConsumer.java
@Component
@RequiredArgsConstructor
class SmsStreamConsumer implements StreamListener<String, MapRecord<String, String, String>> {
    private final StringRedisTemplate redis;
    private final SmsGateway gateway;

    @Override
    public void onMessage(MapRecord<String, String, String> rec) {
        gateway.send(rec.getValue().get("tel"), rec.getValue().get("matn"));   // idempotent bo'lsin!
        redis.opsForStream().acknowledge("notify", rec);                       // XACK
    }
}

@Bean
Subscription smsSubscription(RedisConnectionFactory cf, SmsStreamConsumer consumer) {
    var opts = StreamMessageListenerContainer.StreamMessageListenerContainerOptions.builder()
        .pollTimeout(Duration.ofSeconds(2)).build();
    var container = StreamMessageListenerContainer.create(cf, opts);
    var sub = container.receive(Consumer.from("notify", podName()),
                                StreamOffset.create("sms:outbox", ReadOffset.lastConsumed()), consumer);
    container.start();
    return sub;
}

04

Redis trek: yakuniy suhbat savollari

50–56-modullardan eng ko‘p so‘raladiganlar. Avval o‘zingiz javob bering, keyin oching.

?Redis nima uchun tez va qanday cheklovlari bor?›
RAM, bitta ipli bajarilish (lock yo‘q), epoll, ixcham tuzilmalar. Cheklovlar: xotira hajmi, bitta sekin buyruq hammani bloklaydi, bitta instance bitta yadroda buyruq bajaradi, asinxron replikatsiya.
?Keshni qanday loyihalaysiz? (to‘liq javob)›
Nima keshlanadi va qancha eskirishga toqat bor → TTL; pattern — cache-aside, yozishda DB’dan keyin DEL (afterCommit); kalit sxemasi va versiya prefiksi; serializatsiya JSON; stampede (lock/SWR), penetration (null/Bloom), avalanche (jitter, HA, lokal kesh); eviction siyosati; monitoring (hit rate, evicted_keys, latency); Redis yiqilsa — DB’ga graceful fallback + circuit breaker.
?Keshdagi va DB’dagi ma’lumot farq qilib qolsa?›
TTL eskirishni chegaralaydi; DEL afterCommit; delayed double delete; CDC (Debezium) bilan invalidatsiya; muhim ma’lumotda (balans) keshga ishonmaslik.
?Distributed lock’ni Redis’da qanday qilasiz va xavflari?›
SET NX PX + unikal token, Lua bilan tekshirib o‘chirish, watchdog. Xavflar: GC pauza/soat — lock muddati tugab, ikki ega; Redlock bahsi. To‘g‘rilik uchun fencing token yoki DB constraint.
?Rate limiter qanday ishlaydi?›
Token bucket (Lua, hash: tokens+ts) yoki sliding window (ZSET). Atomiklik — Lua. 429 + Retry-After. Kalit: api-key/user/IP. Redis ishlamasa — fail-open/closed qarori.
?Kalit vaqti tugaganda nima bo‘ladi? SET TTL’ga qanday ta’sir qiladi?›
Lazy + active expiration. SET TTL’ni o‘chiradi (KEEPTTL yo‘q bo‘lsa); INCR/HSET saqlaydi.
?Xotira to‘lsa?›
maxmemory-policy: noeviction (OOM xato) yoki allkeys-lru/lfu, volatile-*. Taxminiy LRU (sampling). LFU skanlarga chidamli.
?RDB va AOF? Qaysi birini?›
RDB — snapshot, AOF — jurnal (everysec ≤1 s yo‘qotish), hybrid — ikkalasi. fork + COW xotira o‘sishi.
?Sentinel va Cluster?›
Sentinel — HA failover (kvorum, lider, eng katta offset’li replika). Cluster — 16384 slot bo‘yicha sharding + failover, hash tag, MOVED/ASK, CROSSSLOT.
?Big key va hot key muammolari?›
Big key — bitta kalitda millionlab element: bloklovchi o‘chirish/ko‘chirish, notekis xotira; aniqlash --bigkeys, yechim — bo‘lish, UNLINK. Hot key — bitta kalitga juda ko‘p so‘rov, Cluster’da bitta shard qiziydi; yechim — lokal kesh, replikalardan o‘qish, kalitni nusxalash (kurs:USD:{0..9}).
?Pub/Sub va Streams farqi?›
Pub/Sub — saqlamaydi, oflayn obunachi yo‘qotadi, fan-out. Streams — jurnal, consumer group, ack, PEL, XAUTOCLAIM, qayta o‘qish.
?KEYS * o‘rniga nima va nega?›
SCAN kursor bilan — bloklamaydi (lekin natijada takror bo‘lishi mumkin, ilova buni hisobga olishi kerak).
?Pipeline, MULTI va Lua farqi?›
Pipeline — RTT tejash, atomik emas; MULTI — blok, rollback’siz, shartsiz; Lua — to‘liq atomik mantiq, lekin bloklaydi, qisqa bo‘lishi kerak.
?Sessiyalarni Redis’da saqlash — afzallik va xavf?›
Stateless pod’lar, istalgan pod foydalanuvchini taniydi, TTL bilan avtomatik tugash. Xavf: Redis yiqilsa hamma chiqib ketadi (HA kerak), sessiya ichiga katta obyekt qo‘yish, SET bilan TTL’ni yo‘qotish.
?Vaziyat: OTP xizmatini loyihalang.›
Kalit auth:otp:{tel} = hash(kod), SET NX EX 120 (qayta yuborish oldingisini bosmaydi, cooldown 60 s alohida kalit); urinishlar INCR auth:otp:try:{tel} EX 900, 5 dan oshsa blok; tekshirishda Lua: kodni solishtir + mos kelsa DEL (bir martalik) — atomik; rate limit telefon va IP bo‘yicha; kod — faqat hash; SMS — Streams/Kafka orqali idempotent yuborish.
