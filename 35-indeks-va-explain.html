Indeks va EXPLAIN

"So'rov sekin" — bank backend'ida eng ko'p eshitiladigan shikoyat. 95% holatda javob: indeks yo'q, yoki bor lekin ishlamayapti. Bu modul B-tree ichini ochadi, EXPLAIN'ni o'qishni o'rgatadi va indeks qachon "o'chib qolishini" ko'rsatadi.

01

Poyga: Seq Scan vs Index Scan

200 satrli jadvalda WHERE id = 168. Ikkalasini bir vaqtda ishga tushiring.

Seq Scan (indekssiz)O(n)

0 satr tekshirildi

Index Scan (B-tree)O(log n)

0 qadam
Sariq — tekshirilgan satrlar, binafsha — indeks yo'li, yashil — topildi.
💡 Miqyos
200 satrda farq 168 vs 4. 10 million satrda: 10 000 000 vs ~24. Indeks katta bo'lgani sari ham log₂ bo'yicha juda sekin o'sadi — B-tree'ning butun sehri shunda.
02

B-tree ichida — qidiruv qanday yuradi

B-tree — tartiblangan kalitlar daraxti. Har tugun "yo'l ko'rsatkich": kalit qaysi bolaga tushishini aytadi. Bargda kalit + satr manzili (ctid). Barglar zanjirlangan — diapazon (BETWEEN) shunchaki yon-veriga yurish.

🎯 Suhbatda
"Nega B-tree, binary tree emas?" — Disk sahifalarda (8 KB) o'qiladi. B-tree tuguni bitta sahifaga sig'adi va yuzlab kalit saqlaydi → daraxt past (3–4 daraja million satr uchun) → 3–4 ta disk o'qish. Binary tree 20+ daraja — 20+ disk o'qish.
03

EXPLAIN ANALYZE — rejani o'qish

Baza so'rovni qanday bajarganini aytib beradi. Har qatorga bosing. Qizil — muammo belgisi, yashil — yaxshi.

psql
EXPLAIN (ANALYZE, BUFFERS)
SELECT t.* FROM tranzaksiya t JOIN hisob h ON h.id = t.hisob_id
WHERE h.mijoz_id = 42 AND t.vaqt > now() - interval '30 days';
Reja pastdan yuqoriga (ichkaridan tashqariga) o'qiladi. Qatorga bosing.

Jadval: mijoz(id, email, ism, holat, tug_sana), indekslar: (email), (holat, tug_sana). Har so'rovga bosing — planner indeksni oladimi?

So'rovni tanlang.
05

Indeks turlari va maxsus indekslar

B-tree (default)

=, <, >, BETWEEN, ORDER BY, LIKE 'abc%'. 95% holat. PK/UNIQUE avtomatik B-tree.

Hash

Faqat =. B-tree'dan sal kichik; kamdan-kam kerak.

GIN

jsonb (@>), massiv, full-text search (tsvector), trigram (LIKE '%abc%' uchun pg_trgm).

GiST / SP-GiST

Geometriya, diapazonlar (tsrange overlap), yaqinlik qidiruvi (PostGIS).

BRIN

Juda katta, tabiiy tartiblangan jadvallar (vaqt bo'yicha loglar). Kichik, "blok diapazoni" indeksi.

indexes.sql
-- Composite: chap ustundan boshlab ishlaydi (holat), (holat, sana), lekin faqat (sana) — yo'q
CREATE INDEX ix_tx_hisob_vaqt ON tranzaksiya (hisob_id, vaqt DESC);

-- Partial: faqat kerakli qism — kichik va tez
CREATE INDEX ix_tx_kutilmoqda ON tranzaksiya (yaratilgan) WHERE holat = 'KUTILMOQDA';

-- Covering (INCLUDE): jadvalga bormasdan javob — Index Only Scan
CREATE INDEX ix_hisob_mijoz ON hisob (mijoz_id) INCLUDE (raqam, valyuta);

-- Expression: funksiya natijasiga
CREATE INDEX ix_mijoz_email_lower ON mijoz (lower(email));

-- Prod'da jadvalni bloklamasdan
CREATE INDEX CONCURRENTLY ix_... ON ...;
06

Indeks bepul emas — yozish narxi

Har INSERT/UPDATE/DELETE har indeksni ham yangilaydi. Slayderni suring.

Indekslar soni: 1
⚠ Amaliy qoida
Indeks — WHERE, JOIN ON, ORDER BY'da tez-tez ishlatiladigan va selektiv (ko'p qiymatli) ustunlarga. holat (3 qiymat) uchun oddiy indeks foydasiz — partial indeks qiling. Ishlatilmayotgan indekslarni pg_stat_user_indexes (idx_scan = 0) orqali toping va o'chiring.
07

Suhbat savollari

?Indeks nima va qanday ishlaydi?›
Ustun qiymatlarini tartiblab saqlovchi alohida struktura (default B-tree) — har kalit yonida satr manzili (ctid). Qidiruv daraxt bo'ylab O(log n) qadamda bargga tushadi, keyin heap'dan satrni oladi. Yozishda indeks ham yangilanadi, joy egallaydi.
?Seq Scan, Index Scan, Index Only Scan, Bitmap Scan farqi?›
Seq — butun jadval (kichik jadval yoki ko'p satr kerak bo'lsa to'g'ri tanlov!). Index Scan — indeks → har mos satr uchun heap'ga boradi (kam satr uchun). Index Only — kerakli ustunlar indeksda bor, heap'ga bormaydi (visibility map yordamida). Bitmap — o'rtacha ko'p satr: avval indeksdan sahifalar bitmap'i, keyin heap'ni tartibli o'qish.
?Indeks bor, lekin planner ishlatmayapti — sabablari?›
1) Ustunga funksiya/cast (lower(email), id::text) — expression index kerak. 2) LIKE '%abc' — oldindan wildcard. 3) Composite indeksning chap ustuni WHERE'da yo'q. 4) Selektivlik past — satrlarning 20–30%+ kerak, Seq Scan arzonroq. 5) Kichik jadval. 6) Statistika eskirgan — ANALYZE. 7) Tip mos emas (bigint ustun vs numeric parametr).
?EXPLAIN va EXPLAIN ANALYZE farqi?›
EXPLAIN — faqat reja va taxminiy cost (bajarilmaydi). ANALYZE — haqiqatda bajaradi, actual time/rows beradi. Taxminiy rows vs actual rows farqi katta bo'lsa — statistika muammosi. UPDATE/DELETE'ni ANALYZE qilsangiz — tranzaksiya ichida, ROLLBACK bilan!
?Composite indeksda ustun tartibi muhimmi?›
Ha — "chap prefiks" qoidasi. (a, b) indeksi WHERE a=…, WHERE a=… AND b=… uchun ishlaydi, faqat WHERE b=… uchun yo'q. Tenglik ustunlari chapga, diapazon (>, BETWEEN) o'ngga: (hisob_id, vaqt).
?N+1 va indeks bog'liqmi? Sekin so'rovni qanday topasiz?›
Alohida muammolar: N+1 — so'rovlar soni (kod), indeks — bitta so'rov tezligi. Topish: pg_stat_statements (eng ko'p vaqt olgan so'rovlar), log_min_duration_statement, keyin EXPLAIN ANALYZE. Spring'da: Hibernate statistikasi, p6spy.
