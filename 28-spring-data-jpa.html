Spring Data JPA

Java obyektlari va baza jadvallari — ikki xil dunyo. JPA (Hibernate) ularni tarjima qiladi. Lekin "sehr" ostida nima bo'ladi? Bu modulda metod nomidan SQL yaratadigan jonli tarjimon va Hibernate'ning "persistence context"ini ko'rasiz.

Maydonni bosing.
Transfer.java
@Entity @Table(name = "transfer", indexes = @Index(columnList = "status, created_at"))
@Getter @Setter @NoArgsConstructor(access = PROTECTED)   // JPA'ga no-arg ctor kerak; @Data EMAS
public class Transfer {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "transfer_seq")
    @SequenceGenerator(name = "transfer_seq", allocationSize = 50)   // batch insert uchun
    private Long id;

    @Column(nullable = false, precision = 19, scale = 2) private BigDecimal amount;
    @Enumerated(EnumType.STRING) private Status status;         // ORDINAL emas — enum tartibi o'zgarsa buziladi
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "from_account_id") private Account from;
    @CreationTimestamp private Instant createdAt;
    @Version private Long version;                               // optimistic lock

    @Override public boolean equals(Object o) {                // id bo'yicha, id null bo'lsa — false
        return o instanceof Transfer t && id != null && id.equals(t.id); }
    @Override public int hashCode() { return getClass().hashCode(); }  // doimiy — Set'da ishlashi uchun
}
02

Metod nomi → SQL: jonli tarjimon

Spring Data metod nomini parse qiladi: findBy + maydon + operator + And/Or + OrderBy. Yozib ko'ring — tokenlar va SQL darhol chiqadi.

Qachon metod nomi yetmaydi
Nom 60+ belgi bo'lsa yoki JOIN/GROUP BY/subquery kerak bo'lsa — @Query (JPQL yoki nativeQuery). Dinamik filtrlar (ixtiyoriy 5 ta parametr) — Specification / Criteria API / QueryDSL. Faqat bir nechta ustun kerak — projection (interface yoki record) — butun entity yuklamang.
TransferRepository.java
interface TransferRepository extends JpaRepository<Transfer, Long>, JpaSpecificationExecutor<Transfer> {

    Page<Transfer> findByStatus(Status s, Pageable p);                 // derived + sahifalash
    Optional<Transfer> findByIdempotencyKey(String key);              // Optional — topilmasa bo'sh
    boolean existsByFromAccountIdAndStatus(Long accId, Status s);     // SELECT 1 ... LIMIT 1 — count emas

    @Query("""
        select new uz.bank.dto.DailyTotal(t.from.id, sum(t.amount))
        from Transfer t
        where t.createdAt >= :from and t.status = 'COMPLETED'
        group by t.from.id
        """)                                                          // JPQL: entity va maydon nomlari, jadval emas
    List<DailyTotal> dailyTotals(@Param("from") Instant from);

    @Query(value = "select * from transfer where amount > :a and created_at > now() - interval '1 day'",
           nativeQuery = true)                                          // Postgres'ga xos sintaksis kerak bo'lsa
    List<Transfer> bigToday(@Param("a") BigDecimal a);

    @Modifying @Query("update Transfer t set t.status = 'EXPIRED' where t.status = 'PENDING' and t.createdAt < :b")
    int expire(@Param("b") Instant before);                             // bulk — persistence context'ni chetlab o'tadi!

    interface TransferSummary { Long getId(); BigDecimal getAmount(); }  // projection
    List<TransferSummary> findByStatusOrderByCreatedAtDesc(Status s);
}

Persistence context: Hibernate'ning "ish stoli"

Suhbatning eng chuqur savoli. Tranzaksiya ichida yuklangan entity'lar persistence context'da (1-darajali kesh) turadi. Siz maydonni o'zgartirasiz — save() chaqirmaysiz — commit'da Hibernate o'zi UPDATE yozadi (dirty checking). Kuzating:

@Transactional void tasdiqla(Long id) {
  Transfer t = repo.findById(id).orElseThrow();
  Transfer t2 = repo.findById(id).orElseThrow(); // yana?
  t.setStatus(COMPLETED); // save() YO'Q
  Transfer n = new Transfer(...); repo.save(n);
} // commit → flush
t.setStatus(FAILED); // tranzaksiyadan tashqarida

Entity holatlari: transient/new (new qilingan, context'da yo'q) → persist/save → managed (context kuzatadi, dirty checking ishlaydi) → tx tugadi → detached (o'zgarish bazaga bormaydi; merge bilan qaytariladi) → remove → removed. save() — id null bo'lsa persist, aks holda merge (SELECT + UPDATE).

05

Suhbat savollari

?JPA, Hibernate, Spring Data JPA farqi?
JPA — spetsifikatsiya (interfeyslar/annotatsiyalar: @Entity, EntityManager, JPQL). Hibernate — JPA'ning eng mashhur implementatsiyasi (+ o'z kengaytmalari). Spring Data JPA — Hibernate/JPA ustidagi qatlam: Repository abstraksiyasi, metod nomidan so'rov, sahifalash, auditing — boilerplate'ni yo'qotadi. JDBC — eng past qatlam, hammasi u orqali.
?Persistence context nima? 1-darajali kesh?
EntityManager'ga bog'langan, tranzaksiya davomida yashaydigan managed entity'lar to'plami. Vazifalari: identity (bir tx'da bir ID = bir obyekt), 1-darajali kesh (takror findById SQL ketmaydi), dirty checking (flush'da snapshot bilan solishtirib UPDATE), write-behind (SQL'ni flush'gacha kechiktirib batch qilish). 2-darajali kesh — SessionFactory darajasida, tx'lar orasida (Ehcache/Redis), alohida yoqiladi.
?Entity holatlari: transient, managed, detached, removed?
Transient — new, context bilmaydi. Managed — persist/find'dan keyin, context kuzatadi, o'zgarish flush'da bazaga boradi. Detached — context yopildi (tx tugadi) yoki detach/clear; o'zgarish bazaga bormaydi, merge() bilan managed nusxa olinadi. Removed — remove() chaqirilgan, flush'da DELETE. save(): id null → persist, aks holda merge.
?Dirty checking nima? save() chaqirish shartmi?
Flush vaqtida Hibernate har managed entity'ni yuklangan snapshot bilan solishtiradi, farq bo'lsa UPDATE yaratadi. Shuning uchun @Transactional ichida findById → setX() yetarli, save() no-op. Kamchilik: ko'p entity'da flush qimmat (hammasi tekshiriladi); readOnly=true tranzaksiyada snapshot saqlanmaydi — tezroq.
?IDENTITY va SEQUENCE farqi?
IDENTITY — baza ID beradi, Hibernate ID'ni bilish uchun INSERT'ni darhol bajarishga majbur → JDBC batch ishlamaydi. SEQUENCE — Hibernate sequence'dan ID oladi (allocationSize=50 bilan 50 ta bir so'rovda), INSERT flush'gacha kechiktiriladi → batch mumkin (hibernate.jdbc.batch_size). PostgreSQL'da SEQUENCE tavsiya. UUID — global unikal, lekin random UUID B-tree indeksni parchalaydi (v7 yaxshiroq).
?JPQL va native query farqi? Qachon qaysi?
JPQL — entity va maydon nomlari bilan, baza-mustaqil, natija entity/DTO (select new). Native — xom SQL, Postgres'ga xos funksiyalar (jsonb, window, CTE, interval) uchun; natija mapping qo'lda (interface projection yoki @SqlResultSetMapping). Default JPQL/derived; murakkab hisobot/optimallashtirish — native.
?@Modifying so'rovdan keyin nega eski ma'lumot ko'rinadi?
Bulk UPDATE/DELETE bazaga to'g'ridan-to'g'ri ketadi, persistence context'dagi entity'lar yangilanmaydi — keyin findById eski (keshdagi) holatni qaytaradi. Yechim: @Modifying(clearAutomatically = true, flushAutomatically = true) yoki bulk'dan keyin entity'larni qayta yuklamaslik.
?Entity'da equals/hashCode qanday yoziladi? Nega @Data yomon?
Lombok @Data hamma maydon bo'yicha equals/hashCode + toString yaratadi: lazy bog'lanishlar yuklanadi (LazyInitializationException / N+1), bidirectional'da cheksiz rekursiya, hashCode id saqlangach o'zgaradi (Set buziladi). To'g'ri: equals — id bo'yicha (id null bo'lsa false, instanceof bilan proxy'ni hisobga olib), hashCode — doimiy (getClass().hashCode()) yoki biznes kalit (UUID) bo'yicha.
?ddl-auto=update prod'da nega xavfli?
Ustun o'chirmaydi, nom o'zgarishini yangi ustun deb tushunadi (ma'lumot yo'qoladi), tip o'zgartirmaydi, indeks/constraint'larni to'liq boshqarmaydi, o'zgarishlar review'siz va qaytarib bo'lmaydi. Prod: validate (sxema mos kelmasa startup xatosi) + Flyway/Liquibase versiyalangan migratsiyalar.
?open-in-view nima, nega o'chirish kerak?
OSIV (Open Session In View): Hibernate sessiyasi butun HTTP so'rov davomida ochiq — controller/serializatsiyada lazy yuklash ishlaydi. Zarari: DB ulanish so'rov oxirigacha band (pool tugaydi), N+1 view'da yashirin, tranzaksiya chegarasi noaniq. spring.jpa.open-in-view=false; kerakli ma'lumotni service'da JOIN FETCH/DTO bilan yuklang.
