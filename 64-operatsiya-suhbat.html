🌊 Kafka Streams

Java kutubxonasi (alohida cluster emas): topic’lardan o‘qib, filter/map/join/agregat qilib, topic’ga yozadi. Holat lokal RocksDB’da, zaxirasi changelog topic’da. exactly_once_v2. Fraud qoidalari, real vaqt agregatlari uchun.

FraudTopology.java — Kafka Streams
builder.stream("tolovlar", Consumed.with(Serdes.String(), paymentSerde))    // kalit = karta raqami
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
    .count()                                                                   // 1 daqiqadagi to'lovlar soni
    .toStream()
    .filter((card, cnt) -> cnt >= 5)                                           // 1 daqiqada 5+ to'lov — shubhali
    .map((w, cnt) -> KeyValue.pair(w.key(), new FraudAlert(w.key(), cnt)))
    .to("fraud-alertlar", Produced.with(Serdes.String(), alertSerde));

06

Kafka trek: yakuniy suhbat savollari

57–64-modullardan eng ko‘p so‘raladiganlar. Avval o‘zingiz javob bering.

?Kafka va RabbitMQ farqi?›
Kafka — taqsimlangan log: xabar o‘qilgach qoladi, consumer offset’ni o‘zi boshqaradi, replay, juda yuqori throughput, tartib partition ichida. RabbitMQ — broker navbatlari: xabar ack’dan keyin o‘chadi, boy marshrutlash (exchange), per-message TTL/priority, vazifa navbatlari uchun qulay.
?Partition, offset, consumer group — bir jumlada har biri.›
Partition — topic’ning tartiblangan, append-only bo‘lagi (tartib va parallellik birligi). Offset — partition ichidagi xabar raqami. Consumer group — partition’larni a’zolar orasida bo‘lishadigan mantiqiy o‘quvchi, o‘z offset’lariga ega.
?Xabar yo‘qolmasligini qanday kafolatlaysiz (producer → broker → consumer)?›
Producer: acks=all, idempotence, retries + delivery.timeout, callback’da xatoni qayta ishlash yoki Outbox. Broker: RF=3, min.insync=2, unclean election o‘chiq, rack awareness. Consumer: auto commit o‘chiq, qayta ishlashdan keyin commit, DLT, idempotent qayta ishlash.
?Dublikatlar qayerdan keladi va qanday himoyalanasiz?›
Producer retry (idempotent producer yopadi), ilova qayta yuborishi yoki Outbox relay (at-least-once), consumer commit’dan oldin yiqilishi/rebalance. Himoya — idempotent consumer (event_id bo‘yicha dedup bitta DB tranzaksiyasida).
?Tartibni qanday kafolatlaysiz?›
Tartib muhim obyekt ID’si kalit bo‘ladi (bitta partition), idempotent producer (retry tartibni buzmaydi), consumer partition’ni ketma-ket qayta ishlaydi, blocking retry (non-blocking tartibni buzadi), partition sonini o‘zgartirmaslik.
?Rebalance muammolari va ularni kamaytirish?›
Eager’da butun group to‘xtaydi, sekin consumer max.poll.interval’dan oshib sikl hosil qiladi. Yechimlar: CooperativeStickyAssignor yoki KIP-848, static membership, max.poll.records ni kamaytirish, qayta ishlashni tezlashtirish, graceful shutdown.
?Exactly-once Kafka’da qanday ishlaydi va chegarasi?›
Idempotent + transaksional producer; read-process-write’da chiqish xabarlari va consumer offset’lari bitta tranzaksiyada; consumer read_committed. Faqat Kafka ichida; tashqi DB/API bilan — idempotentlik.
?Consumer lag o‘sayotganini qanday aniqlaysiz va hal qilasiz?›
kafka-consumer-groups --describe, lag exporter + alert. Bitta partition’da bo‘lsa — hot key yoki zaharli xabar; hammasida — throughput yetmaydi: consumer’ni tezlashtirish, pod qo‘shish (partition sonigacha), batch listener, partition qo‘shish (ehtiyotkorlik bilan).
?ISR, HW, min.insync.replicas — ular qanday bog‘liq?›
ISR — sinxron replikalar; HW — ISR’dagi minimal LEO, consumer faqat HW gacha ko‘radi; min.insync — acks=all yozuvi uchun ISR’ning minimal hajmi. RF=3/min.insync=2 — bitta broker yo‘qotishga chidamli.
?Outbox pattern va nima uchun kerak?›
DB o‘zgarishi va hodisani atomik qilish uchun: hodisa biznes yozuvi bilan bitta tranzaksiyada outbox jadvaliga, relay (Debezium/poller) Kafka’ga uzatadi. At-least-once — consumer idempotent.
?Saga nima?›
Servislar aro jarayon lokal tranzaksiyalar ketma-ketligi sifatida; xato bo‘lsa kompensatsiya tranzaksiyalari. Choreography (hodisalar) yoki orchestration (koordinator). Izolyatsiya yo‘q — PENDING/HOLD holatlari.
?Retention va compaction farqi?›
Retention (delete) — vaqt/hajm bo‘yicha eski segmentlarni o‘chiradi. Compaction — kalit bo‘yicha oxirgi qiymatni saqlaydi, tombstone bilan o‘chiradi; holat topic’lari uchun.
?Schema evolyutsiyasini qanday boshqarasiz?›
Schema Registry + Avro/Protobuf, moslik rejimi (odatda BACKWARD), yangi maydonlar default bilan, maydonni o‘chirish/tipni o‘zgartirish bosqichma-bosqich, CI’da moslik tekshiruvi.
?Kafka’da xavfsizlik?›
TLS (SASL_SSL), autentifikatsiya (SCRAM, mTLS yoki OAUTHBEARER/OIDC), ACL (servis faqat o‘z topic’i va group’iga), sezgir ma’lumotni payload’ga qo‘ymaslik yoki shifrlash, audit.
?Kafka qachon to‘g‘ri tanlov emas?›
Kichik tizim va past hajm, so‘rov-javob, per-message priority/TTL/delay kerak bo‘lsa, operatsion resurs yo‘q bo‘lsa. Shunda RabbitMQ, Redis Streams yoki oddiy DB navbat (SKIP LOCKED) yetadi.
