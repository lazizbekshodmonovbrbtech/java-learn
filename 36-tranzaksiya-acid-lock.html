03

MVCC — nega o'quvchi yozuvchini kutmaydi

PostgreSQL UPDATE'da satrni ustiga yozmaydi — yangi versiya yaratadi. Har tranzaksiya o'z "snapshot"ini ko'radi. Qadamlab ko'ring.

⚠ Oqibati
Ko'p UPDATE = ko'p o'lik versiya (bloat). autovacuum ularni tozalaydi; o'chirilsa jadval shishadi, indekslar sekinlashadi. Uzoq ochiq tranzaksiya (idle in transaction) vacuum'ga to'sqinlik qiladi — Spring'da tranzaksiyani qisqa tuting.
04

SELECT … FOR UPDATE — pessimistik lock

Ikki kassir 1000 so'mlik hisobdan bir vaqtda 800 yechmoqchi. Lock'siz — ikkisi ham "1000 bor" deb ko'radi va balans −600 bo'ladi. Lock bilan — ikkinchisi kutadi.

Kassir 2 — 800 yechish

withdraw.sql / Java
BEGIN;
SELECT balans FROM hisob WHERE id = 1 FOR UPDATE;   -- satr qulflandi, boshqalar kutadi
-- Java'da tekshiruv: balans >= 800 ?
UPDATE hisob SET balans = balans - 800 WHERE id = 1;
COMMIT;                                              -- qulf bo'shadi

-- Eng yaxshisi: tekshiruvni UPDATE ichiga, atomar
UPDATE hisob SET balans = balans - 800 WHERE id = 1 AND balans >= 800;  -- 0 satr → mablag' yetarli emas

06

Suhbat savollari

?ACID nima? Har harfga bank misoli.›
Atomicity — o'tkazmada yechish+qo'shish birga yoki hech biri. Consistency — balans ≥ 0 CHECK hech qachon buzilmaydi. Isolation — hisobot o'rtasida boshqa kassirning yarim o'tkazmasi ko'rinmaydi. Durability — "o'tdi" degan SMS ketgach, server o'chsa ham pul o'tgan bo'ladi (WAL).
?Izolyatsiya darajalari va PostgreSQL default?›
Default READ COMMITTED: har statement o'z snapshot'ini oladi — non-repeatable read mumkin. REPEATABLE READ: butun tranzaksiya bitta snapshot (MVCC), phantom ham yo'q, konfliktda serialization xatosi. SERIALIZABLE: SSI — ketma-ketlikka teng, retry shart. Dirty read PostgreSQL'da yo'q.
?MVCC nima?›
Multi-Version Concurrency Control: UPDATE yangi satr versiyasini yaratadi (xmin/xmax bilan), eski qoladi. Har tranzaksiya snapshot'iga ko'ra "ko'rinadigan" versiyani o'qiydi — o'quvchi yozuvchini bloklamaydi va aksincha. Narxi: o'lik versiyalar, VACUUM kerak.
?Optimistik va pessimistik lock farqi? Qachon qaysi?›
Pessimistik (FOR UPDATE): satr qulflanadi, boshqalar kutadi — konflikt ko'p bo'lganda (balans yechish). Optimistik (@Version): qulf yo'q, saqlashda versiya solishtiriladi, mos kelmasa xato → retry — konflikt kam bo'lganda (profil tahrirlash). Pul operatsiyalarida ko'pincha pessimistik yoki atomar UPDATE ... WHERE balans >= x.
?Deadlock nima, qanday oldini olasiz?›
Ikki tranzaksiya bir-biri qulflagan resursni kutadi — abadiy. PostgreSQL aniqlab bittasini bekor qiladi. Oldini olish: resurslarni bir xil tartibda qulflash (id bo'yicha), qisqa tranzaksiya, kerak bo'lsa lock_timeout, xato bo'lsa retry.
?Lost update'ni qanday hal qilasiz?›
1) Atomar UPDATE: SET balans = balans - 800 WHERE balans >= 800 (o'qib-hisoblab-yozish o'rniga). 2) SELECT FOR UPDATE. 3) @Version optimistik. 4) REPEATABLE READ/SERIALIZABLE + retry. Eng oddiy va tez — 1-usul.
?WAL nima, nega Durability uchun muhim?›
Write-Ahead Log — o'zgarish avval ketma-ket log fayliga yoziladi va fsync qilinadi, keyin (kechroq) jadval sahifalariga. COMMIT = WAL diskda. Server o'chsa WAL qayta o'ynatiladi. Replikatsiya va PITR (nuqtaga qaytish) ham WAL asosida.
