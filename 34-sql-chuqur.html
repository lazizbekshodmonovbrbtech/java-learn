SQL chuqur: JOIN, CTE, window

SQL "nima kerak"ni aytadi, baza "qanday olish"ni o'zi hal qiladi. Lekin so'rov qanday bajarilishini tushunmasangiz, natija kutilmagan bo'ladi. Bu modulda har bosqichda satrlar qanday kamayib-ko'payishini ko'rasiz.

01

So'rov yozilish tartibi ≠ bajarilish tartibi

Siz SELECT'dan boshlab yozasiz, baza FROM'dan boshlab bajaradi. Shuning uchun WHERE'da alias ishlamaydi, HAVING'da esa agregat ishlaydi. 10 ta tranzaksiya ustida qadamlab yuring.

hisobot.sql
SELECT   hisob_id, COUNT(*) AS soni, SUM(summa) AS jami
FROM     tranzaksiya
WHERE    holat = 'OK'
GROUP BY hisob_id
HAVING   SUM(summa) > 150000
ORDER BY jami DESC
LIMIT    1;
🎯 Suhbatda
"WHERE va HAVING farqi?" — WHERE guruhlashdan oldin satrlarni filtrlaydi (agregat ishlatib bo'lmaydi). HAVING guruhlashdan keyin guruhlarni filtrlaydi (agregat bilan). WHERE'ni iloji boricha ko'proq ishlating — kamroq satr guruhlanadi.

⚠ LEFT JOIN + WHERE tuzog'i
LEFT JOIN hisob h ON … WHERE h.valyuta = 'UZS' — WHERE NULL satrlarni o'chiradi, LEFT JOIN INNER'ga aylanadi! Shartni ON ichiga qo'ying: ON h.mijoz_id = m.id AND h.valyuta = 'UZS'.

04

CTE (WITH) — so'rovni bosqichlarga bo'lish

cte.sql
WITH oylik AS (                                   -- 1-qadam: har hisobning oylik aylanmasi
    SELECT hisob_id, date_trunc('month', vaqt) AS oy, SUM(summa) AS jami
    FROM tranzaksiya WHERE holat = 'OK'
    GROUP BY hisob_id, date_trunc('month', vaqt)
),
faol AS (                                          -- 2-qadam: 3 oydan ko'p faol bo'lganlar
    SELECT hisob_id FROM oylik GROUP BY hisob_id HAVING COUNT(*) >= 3
)
SELECT m.ism, o.oy, o.jami                            -- 3-qadam: yakuniy hisobot
FROM oylik o
JOIN faol f ON f.hisob_id = o.hisob_id
JOIN hisob h ON h.id = o.hisob_id
JOIN mijoz m ON m.id = h.mijoz_id
ORDER BY m.ism, o.oy;

-- Rekursiv CTE: filial ierarxiyasi (bosh ofis → viloyat → tuman)
WITH RECURSIVE daraxt AS (
    SELECT id, nom, ota_id, 1 AS daraja FROM filial WHERE ota_id IS NULL
    UNION ALL
    SELECT f.id, f.nom, f.ota_id, d.daraja + 1 FROM filial f JOIN daraxt d ON f.ota_id = d.id
)
SELECT * FROM daraxt ORDER BY daraja;

CTE afzalligi

O'qiladi — yuqoridan pastga qadamlar. Bir nomni bir necha marta ishlatish. Rekursiya (daraxt, graf). PostgreSQL 12+ CTE'ni inline qiladi (optimizatsiya to'sqinlik emas); MATERIALIZED bilan majburlash mumkin.

Subquery vs CTE

Ikkalasi bir xil natija. Subquery ichma-ich o'qish qiyin; CTE — nomlangan bosqich. 2+ marta ishlatilsa yoki ichma-ichlik 2 darajadan oshsa — CTE.

05

Window funksiyalar — guruhlab, lekin satrlarni yo'qotmasdan

GROUP BY satrlarni "yig'ib" 1 ta qiladi. Window — har satr o'z o'rnida qoladi, yoniga guruh bo'yicha hisob qo'shiladi. Funksiyani tanlang — yangi ustun paydo bo'ladi. Rang — PARTITION (hisob).

💡 Bank klassikasi
"Har hisobning oxirgi tranzaksiyasi": ROW_NUMBER() OVER (PARTITION BY hisob_id ORDER BY vaqt DESC) → tashqi so'rovda WHERE rn = 1. Yoki PostgreSQL'ga xos: SELECT DISTINCT ON (hisob_id) * FROM tranzaksiya ORDER BY hisob_id, vaqt DESC.
06

NULL — uch qiymatli mantiq

NULL "noma'lum" degani, "bo'sh" emas. Har ifodani bosing — natijasi TRUE / FALSE / NULL.

Ifodani tanlang
⚠ NOT IN tuzog'i
WHERE id NOT IN (SELECT mijoz_id FROM hisob) — subquery'da bitta NULL bo'lsa, butun natija bo'sh! (x ≠ NULL → NULL → satr chiqmaydi). Yechim: NOT EXISTS yoki WHERE mijoz_id IS NOT NULL.
07

Suhbat savollari

?SQL so'rovi qanday tartibda bajariladi?›
FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT (ifodalar, alias) → DISTINCT → ORDER BY → LIMIT/OFFSET. Shuning uchun WHERE'da SELECT alias'i ishlamaydi, ORDER BY'da ishlaydi.
?INNER, LEFT, RIGHT, FULL, CROSS farqi?›
INNER — faqat mos juftliklar. LEFT — chapning hammasi + mos o'ng (yo'q bo'lsa NULL). RIGHT — teskarisi. FULL — ikkalasining hammasi. CROSS — dekart ko'paytma (n×m), ON yo'q. Amalda 95% INNER va LEFT.
?IN, EXISTS, JOIN — qaysi tez?›
Zamonaviy PostgreSQL planner ko'pincha bir xil rejaga keltiradi (semi-join). EXISTS — birinchi mos topilganda to'xtaydi, NULL'dan xavfsiz. IN — kichik ro'yxat uchun qulay. JOIN — o'ng jadvaldan ustun ham kerak bo'lsa; lekin takrorlanish (dublikat) chiqishi mumkin — DISTINCT kerak bo'ladi. Javob: EXPLAIN bilan tekshiring.
?Window funksiya va GROUP BY farqi?›
GROUP BY guruhni bitta satrga yig'adi (satrlar yo'qoladi). Window (OVER) — har satr qoladi, yoniga guruh bo'yicha hisob qo'shiladi: running total, rank, oldingi/keyingi satr (LAG/LEAD), foiz ulushi. PARTITION BY — guruh, ORDER BY — frame tartibi.
?RANK, DENSE_RANK, ROW_NUMBER farqi?›
Teng qiymatlarda: ROW_NUMBER — baribir 1,2,3 (tasodifiy tartib). RANK — 1,1,3 (bo'shliq qoldiradi). DENSE_RANK — 1,1,2 (bo'shliqsiz). "Top-3 mijoz" — DENSE_RANK; "har guruhdan bittasi" — ROW_NUMBER.
?UNION va UNION ALL?›
UNION dublikatlarni olib tashlaydi (sort/hash — qimmat). UNION ALL — shunchaki qo'shadi, tez. Dublikat bo'lishi mumkin emasligini bilsangiz — doim ALL.
?N+1 muammosini SQL darajasida qanday hal qilasiz?›
Bitta JOIN so'rov yoki WHERE id IN (...) batch. JPA'da JOIN FETCH / @EntityGraph (29-modul). Ro'yxat + har element uchun alohida so'rov — hech qachon.
