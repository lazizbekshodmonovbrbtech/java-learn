Topic, partition, offset

Topic — bu bitta jurnal emas, balki bir nechta mustaqil jurnallar (partition’lar) to‘plami. Partition — Kafka’dagi tartib, parallellik va masshtab birligi. Bu modulning asosiy savoli: "Xabarim qaysi partition’ga tushadi va bu nimaga ta’sir qiladi?"

01

Kalit → partition: haqiqiy hisob

Kafka Java producer’i kalitni murmur2 bilan xeshlaydi va partition’lar soniga bo‘ladi. Quyidagi hisoblagich Kafka’ning aynan o‘sha algoritmi (test vektorlari bilan tekshirilgan). Hisob raqamini kiriting.

02

Xabarlar oqimi: kalit bo‘yicha taqsimot

To‘rtta mijozning to‘lovlari keladi. Rang — hisob (kalit). Bir xil kalit har doim bir xil partitionga tushadi va u yerda tartib saqlanadi. "Kalitsiz" rejimini ham sinang.

💡 Kalitsiz xabarlar: sticky partitioner
Kalit null bo‘lsa, Kafka 2.4+ xabarlarni tasodifiy emas, batch bo‘yicha taqsimlaydi: batch to‘lguncha bitta partition’ga yozadi, keyin boshqasiga o‘tadi (3.3+ da broker yuklamasini ham hisobga oladi). Natija — kattaroq batch, kamroq so‘rov, lekin tartib kafolati yo‘q.
03

Nega kalit muhim: tartib

Hisobga ketma-ket 3 hodisa: +500 000 kirim → −300 000 to‘lov → −150 000 to‘lov. Iste’molchi balansni hisoblab, manfiy bo‘lsa rad etadi.

🔑 key = hisob raqami (bitta partition)
🎲 key = null (turli partition’lar, 2 consumer)
🎯 Suhbat: Kafka tartibni kafolatlaydimi?
Faqat bitta partition ichida. Topic bo‘ylab global tartib yo‘q. Shuning uchun tartib muhim bo‘lgan obyekt (hisob, karta, buyurtma) ID’si kalit qilinadi. Global tartib kerak bo‘lsa — 1 partition (parallellik yo‘q). Yana bir shart: producer’da retry bo‘lsa tartib buzilmasligi uchun enable.idempotence=true (59-modul).
04

Partition sonini oshirish xavfi

Kafka partition sonini oshirishga ruxsat beradi (kamaytirishga — yo‘q). Lekin hash % N formulasi o‘zgaradi — kalitlarning ko‘pi boshqa partition’ga "ko‘chadi".

Oldin: 6
⚠️ Amaliy qoida
Partition sonini boshidanoq zaxira bilan tanlang (kutilgan yuk × 2–3). Oshirish kerak bo‘lsa: eski partition’lardagi barcha xabarlar iste’mol qilinguncha kuting yoki yangi topic yarating va migratsiya qiling. Kalit bo‘yicha holat saqlaydigan (stateful) iste’molchilar uchun bu ayniqsa xavfli.

06

Diskda partition: segmentlar va retention

Har partition — papka, ichida segment fayllar. Yozish faqat faol segmentga. Retention eski segmentlarni butunligicha o‘chiradi.

Papka: /var/kafka/data/tolovlar-0/
terminal
kafka-topics.sh --bootstrap-server kafka:9092 --create --topic tolovlar \
    --partitions 12 --replication-factor 3 \
    --config retention.ms=604800000 \
    --config segment.bytes=1073741824 \
    --config min.insync.replicas=2
# retention.ms = 7 kun, segment.bytes = 1 GB

kafka-topics.sh --bootstrap-server kafka:9092 --describe --topic tolovlar
# Topic: tolovlar  PartitionCount: 12  ReplicationFactor: 3
#   Partition: 0  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1

kafka-get-offsets.sh --bootstrap-server kafka:9092 --topic tolovlar      # har partition oxirgi offset
07

Suhbat savollari

?Partition nima va nima uchun kerak?›
Topic’ning mustaqil, tartiblangan, append-only bo‘lagi. U parallellik birligi (bir group’da bitta partition’ni bitta consumer o‘qiydi), masshtab birligi (partition’lar broker’larga tarqaladi) va tartib birligi (tartib faqat partition ichida).
?Xabar qaysi partition’ga tushishini nima belgilaydi?›
Producer: aniq partition ko‘rsatilgan bo‘lsa — o‘sha; kalit bor bo‘lsa — murmur2(key) % partitions; kalit null bo‘lsa — sticky partitioner. O‘zingizning Partitioner’ingizni ham yozish mumkin.
?Hisob bo‘yicha hodisalar tartibini qanday kafolatlaysiz?›
Hisob ID’sini kalit qilish (bitta partition), producer’da idempotence (retry tartibni buzmasligi uchun), consumer’da partition ichida ketma-ket qayta ishlash (bir partition’ni parallel thread’larga bo‘lmaslik yoki kalit bo‘yicha bo‘lish).
?Partition sonini oshirsa nima bo‘ladi?›
Yangi xabarlar uchun hash % N o‘zgaradi — bir kalitning eski xabarlari bir partition’da, yangilari boshqasida; o‘tish davrida tartib buziladi, kalit bo‘yicha lokal holat noto‘g‘ri bo‘ladi. Kamaytirib bo‘lmaydi.
?Offset nima va u qayerda saqlanadi?›
Partition ichidagi xabarning ketma-ket raqami. Consumer group’ning commit qilgan offset’i ichki __consumer_offsets topic’ida saqlanadi (compacted). Commit qilinadigan qiymat — keyingi o‘qiladigan xabar offset’i.
?Retention qanday ishlaydi?›
cleanup.policy=delete: segment butunligicha retention.ms yoki retention.bytes oshganda o‘chiriladi (faol segment o‘chirilmaydi). compact: har kalitning oxirgi qiymati qoladi (63-modul).
?Issiq kalit (hot key) muammosi?›
Bitta kalitga juda ko‘p xabar (masalan, katta merchant) — bitta partition va bitta consumer to‘lib ketadi, qolganlari bo‘sh. Yechim: kalitga qo‘shimcha bo‘lak (merchantId + hash(txId) % 4) — agar bu kalit ichida tartib talab qilinmasa.
