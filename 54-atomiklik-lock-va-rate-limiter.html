Atomiklik, lock va rate limiter

Redis bitta ipda ishlaydi — har bitta buyruq atomik. Lekin ikki buyruq orasida boshqa pod’ning buyrug‘i bajarilishi mumkin. Bu modulda "o‘qib-hisoblab-yozish" nega buziladi, uni MULTI, WATCH va Lua bilan qanday tuzatish, taqsimlangan lock’ning nozik tomonlari (GC pauza, fencing token, Redlock bahsi) va bankdagi API limitlari uchun token bucket’ni ko‘ramiz.

01

🎯 Suhbat: Redlock bahsi
Redis muallifi antirez Redlockni taklif qildi: 5 ta mustaqil master, lock ko‘pchilikda (≥3) olinsa — olingan. Martin Kleppmann tanqidi: lock TTL’ga (vaqtga) tayanadi; GC pauza, tarmoq kechikishi yoki soat sakrashi tufayli ikki mijoz o‘zini egasi deb o‘ylashi mumkin — fencing tokensiz to‘g‘rilik kafolati yo‘q. Xulosa: lock samaradorlik uchun (ikki marta bajarilsa ham zarar kichik) — Redis yetarli. To‘g‘rilik uchun (pul!) — resursning o‘zi tekshirishi kerak: DB’da unikal constraint, versiya/fencing, SELECT … FOR UPDATE yoki PG advisory lock.
03

Token bucket: API limitining yuragi

Chelakka soniyasiga r ta token tomadi, sig‘imi b. Har so‘rov bitta token oladi; token yo‘q — 429 Too Many Requests. Portlash (burst) b gacha ruxsat, o‘rtacha tezlik — r.

💧 +2/s
To‘ldirish tezligi r: 2 token/s
Sig‘im b: 5
So‘rov yuboring.
token_bucket.lua
-- KEYS[1] = rl:{api-key}   ARGV: rate, capacity, now_ms, cost
local b = redis.call("HMGET", KEYS[1], "tokens", "ts")
local rate, cap, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)     -- o'tgan vaqt uchun "tomgan" tokenlar
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call("HSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("PEXPIRE", KEYS[1], math.ceil(cap / rate * 1000) * 2)
return { allowed and 1 or 0, tostring(tokens) }
💡 Vaqtni kim beradi?
nowni ilova yuborsa, pod’lar soati farq qilishi mumkin. Redis 5+ da skript ichida redis.call("TIME") ishlatish mumkin (effects replication). Tayyor yechimlar: Bucket4j (Redis/Lettuce backend), Resilience4j RateLimiter (faqat lokal), Spring Cloud Gateway RedisRateLimiter (aynan token bucket + Lua).

05

Suhbat savollari

?Redis’da atomiklik qanday ta’minlanadi?›
Har bir buyruq bitta ipda bajarilgani uchun atomik. Bir nechta buyruq uchun: MULTI/EXEC (blok, lekin rollback yo‘q), WATCH (optimistik CAS), Lua skript yoki Redis Functions (to‘liq atomik mantiq). Pipeline atomik emas — faqat RTT tejaydi.
?MULTI/EXEC relyatsion tranzaksiyadan nimasi bilan farq qiladi?›
Izolyatsiya bor (blok orasiga boshqa buyruq kirmaydi), lekin rollback yo‘q: runtime xato bergan buyruqdan keyingilari baribir bajariladi. Blok ichida o‘qilgan qiymat asosida qaror qilib bo‘lmaydi — buning uchun WATCH yoki Lua.
?Redis’da distributed lock’ni qanday to‘g‘ri qilasiz?›
SET key NX PX ; ochishda Lua bilan "GET == token bo‘lsa DEL". TTL — egasi o‘lsa lock abadiy qolmasligi uchun; token — boshqaning lock’ini o‘chirmaslik uchun. Uzun ish bo‘lsa — TTL’ni uzaytirish (Redisson watchdog). To‘g‘rilik muhim bo‘lsa — fencing token yoki DB darajasidagi kafolat.
?Fencing token nima?›
Har lock olishda monoton o‘suvchi raqam (masalan INCR lock:eod:ver). Resurs (DB) oxirgi ko‘rgan tokendan kichik token bilan kelgan yozuvni rad etadi. Shunda GC pauzadan "uyg‘ongan" eski ega hech narsa buzolmaydi.
?Rate limiter qanday loyihalaysiz?›
Talab: kim bo‘yicha (API kalit, user, IP), qanday limit (o‘rtacha + portlash), qayerda (gateway). Algoritm: token bucket (Lua, atomik) yoki sliding window. Javobda 429 + Retry-After, X-RateLimit-* sarlavhalar. Redis ishlamasa — fail-open yoki fail-closed qarori (to‘lov API uchun odatda closed, o‘qish uchun open).
?Fixed window’ning muammosi?›
Oyna chegarasida limit ikki barobar o‘tishi mumkin: 0.9 s da 5, 1.1 s da yana 5 — 0.2 s ichida 10 so‘rov. Sliding window yoki token bucket buni tuzatadi.
