JPA bog'lanishlar va N+1

Hisobda ko'p o'tkazma bor. Bu "ko'p" ni JPA'da qanday ifodalash? Va nega 5 ta hisobni ko'rsatish uchun 6 ta (100 ta uchun 101 ta) SQL ketadi? JPA'ning eng mashhur muammosi — jonli.

01

Bog'lanish turlari — jadval darajasida

Bazada bog'lanish — bu foreign key ustuni (yoki oraliq jadval). JPA annotatsiyasi shuni tasvirlaydi. Turni tanlang:

Mapping

    

    
Suhbatda so'raladi: owning side
Bidirectional bog'lanishda FK ustuni bor tomon — egasi (owning side); JPA faqat shu tomondagi o'zgarishni bazaga yozadi. mappedBy — "men ega emasman, u tomonga qara". account.getTransfers().add(t) qilib t.setAccount(account) qilmasangiz — FK null qoladi. Shuning uchun helper metod: addTransfer(t){ transfers.add(t); t.setAccount(this); }.

LAZY: kolleksiya birinchi murojaatda yuklanadi — har hisob uchun alohida. Hisoblar sonini oshiring va farqni ko'ring.

    

    

      
Yechimlar

      
// 1. JOIN FETCH — bitta so'rovda hammasi (kolleksiya uchun DISTINCT / Set)
@Query("select distinct a from Account a left join fetch a.transfers where a.customer.id = :cid")
List<Account> withTransfers(Long cid);
// ⚠ ikki kolleksiyani birga fetch qilsangiz — MultipleBagFetchException (List×List). Set ishlating yoki ikki so'rov.
// ⚠ JOIN FETCH + Pageable — Hibernate xotirada sahifalaydi (HHH90003004) — katta jadvalda xavfli.

// 2. @EntityGraph — derived query bilan
@EntityGraph(attributePaths = {"transfers", "customer"})
List<Account> findByStatus(Status s);

// 3. @BatchSize — N+1 o'rniga N/10+1: WHERE account_id IN (?,?,...,?)
@OneToMany(mappedBy = "account") @BatchSize(size = 10) Set<Transfer> transfers;
// global: spring.jpa.properties.hibernate.default_batch_fetch_size=16

// 4. DTO — entity umuman yuklamang, faqat kerakli ustunlar
@Query("select new uz.bank.AccountSummary(a.id, a.number, count(t), sum(t.amount)) from Account a left join a.transfers t group by a.id, a.number")
List<AccountSummary> summaries();

    

  


  

    
03
LAZY: "keyin yuklayman" — lekin qachon?

    
LAZY maydon — Hibernate proxy. Birinchi murojaatda SQL ketadi — agar sessiya (tranzaksiya) hali ochiq bo'lsa. Yopiq bo'lsa — mashhur LazyInitializationException. Kartani bosing:

    

      
❌ Controller'da (tx yo'q, OSIV=false)
Account a = service.get(1);
a.getTransfers().size();
org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role: Account.transfers: could not initialize proxy - no Session

      
✓ @Transactional service ichida
@Transactional(readOnly = true)
int count(Long id) {
  return repo.findById(id).orElseThrow()
    .getTransfers().size();
}
SELECT ... FROM transfer WHERE account_id=1 — sessiya ochiq, yuklandi ✓ (lekin bu ham N+1 bo'lishi mumkin — JOIN FETCH yaxshiroq)

      
❌ Entity'ni JSON'ga berish
@GetMapping("/{id}")
Account get(@PathVariable Long id) {
  return repo.findById(id).get();
}
Jackson getTransfers() ni chaqiradi → LazyInitializationException (yoki OSIV=true bo'lsa N+1 + cheksiz rekursiya: transfer.account.transfers...). Yechim: DTO.

      
✓ DTO bilan
@Transactional(readOnly = true)
AccountDto get(Long id) {
  Account a = repo.findWithTransfers(id);
  return AccountDto.from(a);  // tx ichida
}
Kerakli ma'lumot tx ichida DTO'ga ko'chirildi. Controller entity ko'rmaydi. ✓

    

    
EAGER nega yomon
@ManyToOne default EAGER! Har Transfer yuklanganda Account ham (JOIN yoki alohida SELECT). Account'da EAGER Customer, Customer'da EAGER Branch… — bitta findById butun grafni yuklaydi. Qoida: hamma bog'lanish LAZY, kerak bo'lganda so'rovda fetch. @ManyToOne(fetch = LAZY) ni doim yozing.

  


  

    
04
Cascade va orphanRemoval

    

      
cascade — amal "yuqadi"
@OneToMany(mappedBy="order", cascade = ALL,
           orphanRemoval = true)
List<OrderItem> items;

repo.save(order);   // items ham INSERT
repo.delete(order); // items ham DELETE
order.getItems().remove(0); // orphanRemoval → DELETE
Faqat "ota-bola" (composition) uchun: OrderItem Order'siz ma'nosiz. Transfer→Account'ga cascade qo'ymang — o'tkazmani o'chirib hisobni o'chirib yubormang!

      
Kolleksiya tipi
Set<Transfer>  — dublikat yo'q, ikki JOIN FETCH ok,
                 equals/hashCode kerak
List<Transfer> — tartib, "bag": remove() butun
                 kolleksiyani qayta yozishi mumkin
@OrderBy("createdAt DESC")
Ko'p elementli bog'lanish (hisob → 1 mln o'tkazma) — umuman mapping qilmang, repo orqali sahifalab so'rang.

    

  


  

    
05
Suhbat savollari

    
?N+1 muammosi nima? Qanday aniqlaysiz va hal qilasiz?
1 so'rov bilan N ta ota entity olinadi, keyin har birining LAZY bog'lanishiga murojaat N ta qo'shimcha SELECT beradi. Aniqlash: SQL log (show-sql, datasource-proxy, p6spy), Hibernate statistikasi (hibernate.generate_statistics), testda so'rov sonini assert qilish. Yechim: JOIN FETCH / @EntityGraph (1 so'rov), @BatchSize / default_batch_fetch_size (N/k+1), DTO projection (entity'siz), kerak bo'lmasa umuman yuklamaslik.


?LAZY va EAGER farqi? Default qaysi?
LAZY — bog'lanish birinchi murojaatda yuklanadi (proxy), EAGER — ota entity bilan darhol. Default: @ManyToOne va @OneToOne — EAGER, @OneToMany va @ManyToMany — LAZY. Tavsiya: hammasini LAZY qiling (EAGER global 'har doim yuklash' — nazorat yo'q, kaskadli yuklash), kerak bo'lganda so'rov darajasida fetch.


?LazyInitializationException nima, qanday oldini olasiz?
LAZY proxy'ga sessiya (persistence context) yopilgandan keyin murojaat — Hibernate SQL yubora olmaydi. Sabab: tranzaksiyadan tashqarida (controller, Jackson serializatsiya, async thread). Yechim: kerakli ma'lumotni tranzaksiya ichida yuklash (JOIN FETCH/EntityGraph), DTO'ga tx ichida o'tkazish, Hibernate.initialize(). open-in-view=true 'yashiradi' lekin muammoni kattalashtiradi.


?Owning side va mappedBy?
Bidirectional bog'lanishda bazadagi FK'ni qaysi tomon boshqarishini belgilaydi. Owning side — FK ustuni bor entity (@ManyToOne tomoni, yoki @JoinColumn/@JoinTable qo'yilgan tomon). Inverse side — mappedBy='maydonNomi' bilan; undagi o'zgarish bazaga yozilmaydi. Shuning uchun ikkala tomonni sinxron tutuvchi helper metodlar (addChild/removeChild).


?@OneToMany'da List va Set farqi?
List (bag) — tartib yo'q, dublikat mumkin; remove() Hibernate'da ba'zan butun kolleksiyani o'chirib qayta yozadi; ikkita List'ni JOIN FETCH — MultipleBagFetchException. Set — dublikat yo'q, ikkita Set fetch mumkin, lekin to'g'ri equals/hashCode kerak (id null bo'lganda ham ishlaydigan), va add() har element uchun hashCode → kolleksiya initsializatsiyasi. @OrderColumn bilan List indeksli bo'ladi.


?cascade turlari? Qachon ishlatmaslik kerak?
PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL. orphanRemoval=true — kolleksiyadan olib tashlangan bola DELETE. Faqat composition ('bola otasiz yashamaydi': Order→OrderItem) uchun. Aggregation/reference'da (Transfer→Account, Employee→Department) hech qachon REMOVE/ALL — bola o'chganda ota o'chib ketadi.


?JOIN FETCH bilan sahifalash nega muammo?
Kolleksiya JOIN FETCH natijada ota qatorlari takrorlanadi (har bola uchun); SQL LIMIT qatorlarga qo'llanadi, entity'larga emas. Hibernate 'firstResult/maxResults specified with collection fetch; applying in memory' — butun natijani yuklab, xotirada sahifalaydi. Yechim: 2 so'rov (avval ota ID'larini sahifalab, keyin IN bilan bolalarni), yoki @BatchSize, yoki DTO.


?@ManyToMany o'rniga nima tavsiya qilasiz?
Oraliq jadvalni alohida entity qilib ikki @ManyToOne bilan mapping qilish. Sabab: oraliq jadvalga deyarli doim qo'shimcha ustun kerak bo'ladi (sana, holat, kim qo'shdi), @ManyToMany'da bunga joy yo'q; cascade REMOVE @ManyToMany'da xavfli; so'rovlar aniqroq.
