Validation va xato boshqaruvi

Tashqaridan kelgan ma'lumotga ishonmang. Lekin tekshirish — yarim ish. Ikkinchi yarmi: xato bo'lganda mijozga bir xil, tushunarli, xavfsiz javob qaytarish. Bu ikkalasini jonli ko'rasiz.

01

Jonli validator: o'tkazma so'rovi

DTO maydonlariga cheklov annotatsiyalari, controller'da @Valid — Spring qolganini qiladi. Maydonlarni o'zgartiring yoki tayyor xatolarni bosing:

@NotBlank@Pattern(\d{20})
@NotBlank@Pattern(\d{20})
@Positive@DecimalMax(50000000)@Digits(15,2)
@Pattern([A-Z]{3})
@AssertTrue farqliHisoblar (class-level)
TransferRequest.java
public record TransferRequest(
    @NotBlank @Pattern(regexp = "\\d{20}", message = "hisob 20 raqam") String fromAccount,
    @NotBlank @Pattern(regexp = "\\d{20}")                             String toAccount,
    @NotNull @Positive @DecimalMax("50000000") @Digits(integer = 15, fraction = 2) BigDecimal amount,
    @NotNull @Pattern(regexp = "[A-Z]{3}")                                  String currency,
    @Valid List<@NotBlank String> tags                                  // ichki elementlar ham
) {
    @AssertTrue(message = "hisoblar bir xil bo'lmasin")          // cross-field
    boolean isFarqliHisoblar() { return !fromAccount.equals(toAccount); }
}
// Controller: create(@Valid @RequestBody TransferRequest req)
// Xato → MethodArgumentNotValidException → advice → 400 + maydonlar ro'yxati
Ko'p ishlatiladigan annotatsiyalar
@NotNull (null emas) · @NotBlank (String: null/bo'sh/bo'shliq emas) · @NotEmpty (kolleksiya bo'sh emas) · @Size(min,max) · @Min/@Max (int/long) · @DecimalMin/@DecimalMax, @Positive, @Digits (BigDecimal) · @Pattern · @Email · @Past/@Future · @Valid (ichki obyekt). Diqqat: @NotBlank BigDecimal'ga ishlamaydi — tipga mos tanlang.
02

Exception sayohati: Service → Advice → JSON

Service exception tashladi. U controller orqali yuqoriga chiqadi, @RestControllerAdvice uni ushlab, eng aniq handler'ni tanlaydi. Exception turini tanlang:

Chaqiruv steki (pastdan yuqoriga)
TransferController.create()controller — try/catch YO'Q💥
TransferService.transfer()throw new ...Exception()💥
TransferRepository.save()SQL constraint💥
@RestControllerAdvice — handler'lar (aniqdan umumiyga)
@ExceptionHandler(InsufficientFundsException)→ 422
@ExceptionHandler(NotFoundException)→ 404
@ExceptionHandler(MethodArgumentNotValidException)→ 400 + fieldErrors
@ExceptionHandler(DataIntegrityViolationException)→ 409
@ExceptionHandler(Exception.class)→ 500, traceId, log.error
GlobalExceptionHandler.java
@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(InsufficientFundsException.class)
    ProblemDetail funds(InsufficientFundsException e) {
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, e.getMessage());
        pd.setType(URI.create("https://api.bank.uz/errors/insufficient-funds"));
        pd.setProperty("balance", e.getBalance());       // qo'shimcha maydon
        return pd;                                        // RFC 9457 application/problem+json
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalid(MethodArgumentNotValidException e) {
        var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setProperty("errors", e.getFieldErrors().stream()
            .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage())).toList());
        return pd;
    }

    @ExceptionHandler(Exception.class)                  // oxirgi to'siq
    ProblemDetail other(Exception e, HttpServletRequest r) {
        String traceId = MDC.get("traceId");
        log.error("Unhandled [{}] {}", traceId, r.getRequestURI(), e);   // stack trace — LOG'ga
        var pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Ichki xato");
        pd.setProperty("traceId", traceId);              // mijoz support'ga shu ID'ni aytadi
        return pd;
    }
}
// Boot 3: spring.mvc.problemdetails.enabled=true — standart MVC xatolari ham ProblemDetail

Tekshiruv bitta joyda emas. Har qatlam o'zinikini tekshiradi va o'z status kodini beradi:

UNIQUE, FK, CHECK — oxirgi himoya (race condition'da ham)

Qoida
Bean Validation'da bazaga bormang ("hisob mavjudmi?" — bu biznes qatlam). Bazadagi constraint'ni "validatsiya bor-ku" deb olib tashlamang — ikki parallel so'rov validatsiyadan o'tib, faqat UNIQUE to'xtatadi.
04

Ilg'or: custom, guruh, metod validatsiyasi

Custom annotatsiya

@Target(FIELD) @Retention(RUNTIME)
@Constraint(validatedBy = AccountValidator.class)
@interface ValidAccount {
  String message() default "hisob noto'g'ri";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload() default {};
}
class AccountValidator implements
    ConstraintValidator<ValidAccount, String> {
  public boolean isValid(String v, ConstraintValidatorContext c) {
    return v != null && luhn(v);   // checksum
  }
}
Qayta ishlatiladigan qoida. Validator — Spring bean bo'la oladi (inject mumkin), lekin bazaga bormang.

Guruhlar: yaratish vs yangilash

interface OnCreate {} interface OnUpdate {}
record UserDto(
  @Null(groups=OnCreate.class)
  @NotNull(groups=OnUpdate.class) Long id,

@PostMapping create(@Validated(OnCreate.class) @RequestBody UserDto d)

05

Suhbat savollari

?@Valid va @Validated farqi?
@Valid — Jakarta Bean Validation standarti: obyektni va ichki (nested) obyektlarni tekshiradi, guruhlarni bilmaydi. @Validated — Spring'niki: validatsiya guruhlarini qo'llaydi (@Validated(OnCreate.class)) va klass darajasida qo'yilsa metod parametrlari validatsiyasini (AOP proxy orqali) yoqadi. Nested obyekt uchun @Valid, guruh/servis metodlari uchun @Validated.
?Validatsiya xatosi qaysi exception? Qanday ushlanadi?
@RequestBody + @Valid → MethodArgumentNotValidException (BindingResult bilan, fieldErrors). @RequestParam/@PathVariable yoki @Validated servis metodi → ConstraintViolationException. Form binding → BindException. @RestControllerAdvice'da @ExceptionHandler bilan ushlab, maydon → xabar ro'yxatini 400 bilan qaytarasiz. Boot 3'da ResponseEntityExceptionHandler'ni extend qilib ProblemDetail olish mumkin.
?@ControllerAdvice va @RestControllerAdvice?
Ikkalasi global exception handler, @ModelAttribute, @InitBinder uchun. @RestControllerAdvice = @ControllerAdvice + @ResponseBody — javob JSON'ga seriyalanadi (view emas). basePackages/annotations bilan qamrovni cheklash mumkin. Handler tanlash: exception tipiga eng yaqin (aniq) metod g'olib; bir nechta advice bo'lsa @Order.
?ProblemDetail (RFC 7807/9457) nima?
Xato javobining standart formati: type (URI, xato turi hujjati), title, status, detail, instance + o'zingizning maydonlaringiz. Content-Type: application/problem+json. Spring 6 / Boot 3'da ProblemDetail klassi va spring.mvc.problemdetails.enabled. Foyda: mobil/frontend bitta parser, hujjatlashtirish oson.
?Biznes validatsiya qayerda bo'lishi kerak?
Service qatlamida: 'balans yetarlimi', 'hisob bloklanganmi', 'limit' — bazaga murojaat va tranzaksiya kerak. Bean Validation faqat sintaktik/format (null, uzunlik, regex) — bazaga bormaydi va tez. Baza constraint'lari — oxirgi himoya, ayniqsa race condition uchun (UNIQUE).
?500 xatosida mijozga nima qaytarasiz?
Umumiy xabar + traceId (yoki correlation id). Stack trace, klass nomlari, SQL — hech qachon (xavfsizlik, ichki tuzilma sizadi). Log'ga to'liq stack trace traceId bilan. Boot default'da server.error.include-stacktrace=never. Monitoring (Sentry/ELK) traceId bo'yicha topadi.
?Custom validator qanday yoziladi?
Annotatsiya (@Constraint(validatedBy=...), message/groups/payload majburiy atributlari) + ConstraintValidator implementatsiyasi (isValid). Validator Spring bean bo'la oladi — dependency inject qilinadi. Class-level (cross-field) uchun @Target(TYPE) va obyekt qabul qiluvchi validator, yoki oddiy @AssertTrue metod.
?null keldi — @NotNull, @NotEmpty, @NotBlank qaysi?
@NotNull — faqat null emas ("" o'tadi). @NotEmpty — null emas va size>0 (String, Collection, Map, array; " " o'tadi). @NotBlank — faqat String: null emas, trim()dan keyin bo'sh emas. Odatda String uchun @NotBlank, kolleksiya uchun @NotEmpty, boshqa obyekt uchun @NotNull.
