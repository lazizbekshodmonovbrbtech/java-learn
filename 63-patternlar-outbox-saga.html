Pattern’lar: Outbox, Saga, compaction

Kafka’ni to‘g‘ri ishlatish — konfiguratsiyadan ko‘ra arxitektura masalasi. Bu modulda bank tizimlarida eng ko‘p ishlatiladigan beshta pattern: DB va Kafka’ni ishonchli bog‘lovchi Transactional Outbox, dublikatlarga chidamli idempotent consumer, servislar aro tranzaksiya — Saga, holat saqlovchi compacted topic va sxema nazorati — Schema Registry.

01

Dual write muammosi va Transactional Outbox

To‘lov DB’ga yozilishi va hodisa Kafka’ga ketishi kerak. Ikki alohida tizim — ikki alohida commit. Stsenariyni tanlang, qadamlarni o‘ting.

PaymentService.java — Outbox
@Transactional
public Payment pay(PayCommand cmd) {
    Payment p = payments.save(Payment.from(cmd));                 // 1. biznes yozuvi
    outbox.save(new OutboxEvent(                                  // 2. SHU tranzaksiyada hodisa
        UUID.randomUUID(), "Payment", p.getId().toString(),       //    aggregate_type, aggregate_id (= kalit)
        "PaymentCompleted", json(PaymentEvent.of(p))));
    return p;                                                      // commit: ikkalasi yoki hech biri
}
outbox.sql
CREATE TABLE outbox (
    id             uuid PRIMARY KEY,
    aggregate_type text        NOT NULL,
    aggregate_id   text        NOT NULL,     -- Kafka kaliti → tartib
    type           text        NOT NULL,
    payload        jsonb       NOT NULL,
    created_at     timestamptz NOT NULL DEFAULT now()
);
-- Debezium Outbox Event Router: WAL'dan o'qiydi → topic "Payment" → kalit aggregate_id
-- Polling relay alternativasi: SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100 → send → DELETE
💡 Relay: polling yoki CDC?
Polling (har 500 ms SELECT … FOR UPDATE SKIP LOCKED) — oddiy, qo‘shimcha infratuzilmasiz, lekin DB’ga yuk va kechikish. CDC (Debezium + Kafka Connect, PG logical replication) — WAL’dan o‘qiydi, kechikish past, DB so‘rovsiz; evaziga Connect cluster’ni boshqarish kerak. Ikkalasida ham at-least-once: relay yuborib, belgilashdan oldin yiqilsa — qayta yuboradi. Demak consumer idempotent bo‘lishi shart.
02

Idempotent consumer

CashbackListener.java
@KafkaListener(topics = "Payment", groupId = "cashback")
@Transactional                                             // DB tranzaksiyasi
public void on(PaymentEvent ev, @Header("id") String eventId) {
    int inserted = jdbc.update("""
        INSERT INTO processed_events(consumer, event_id) VALUES ('cashback', ?)
        ON CONFLICT DO NOTHING""", eventId);
    if (inserted == 0) return;                             // allaqachon qayta ishlangan → jim o'tkazib yubor
    cashback.accrue(ev.accountNo(), ev.amount());          // biznes o'zgarishi — SHU tranzaksiyada
}                                                          // commit'dan keyin konteyner offset'ni commit qiladi

Saga: servislar aro "tranzaksiya"

🎯 Saga’ning cheklovi
Saga — ACID emas, izolyatsiya yo‘q: oraliq holatlar (pul yechilgan, lekin kredit bo‘lmagan) boshqalarga ko‘rinadi. Shuning uchun "PENDING/HOLD" holatlari, semantik lock’lar va kompensatsiyalarning o‘zi idempotent va albatta muvaffaqiyatli bo‘lishi (retry bilan) kerak. Pulni yechish o‘rniga avval hold (bron) qilish — keng tarqalgan yondashuv.
04

Compacted topic: har kalitning oxirgi holati

cleanup.policy=compact — Kafka vaqt bo‘yicha emas, kalit bo‘yicha tozalaydi: har kalitning faqat oxirgi qiymati qoladi. Karta holatlari topic’i. Yozuvlarni qo‘shing va compaction’ni ishga tushiring.

Yangi consumer boshidan o‘qisa oladigan holat (KTable):
Kalit = karta ID, qiymat = holat.
💡 Qayerda ishlatiladi
__consumer_offsets — o‘zi compacted topic. Bankda: karta/hisob holatlari, valyuta kurslari, mijoz sozlamalari — yangi servis ishga tushganda topic’ni boshidan o‘qib to‘liq holatni tiklaydi (DB so‘ramasdan). Kafka Streams KTable va CDC snapshot’lari shunga asoslangan.

Suhbat savollari
?Dual write muammosi nima va Outbox uni qanday hal qiladi?›
DB va Kafka’ga alohida yozish atomik emas: biri muvaffaqiyatli, ikkinchisi xato bo‘lishi mumkin (hodisa yo‘qoladi yoki soxta hodisa ketadi). Outbox: hodisa biznes ma’lumoti bilan bitta DB tranzaksiyasida outbox jadvaliga yoziladi, alohida relay (polling yoki Debezium CDC) uni Kafka’ga uzatadi. Natija — at-least-once, shuning uchun consumer idempotent.
?Idempotent consumer qanday yoziladi?›
Har hodisaning unikal ID’si (event_id yoki biznes kaliti) bo‘yicha "qayta ishlandi" belgisi biznes o‘zgarishi bilan bitta tranzaksiyada saqlanadi (INSERT … ON CONFLICT DO NOTHING); allaqachon bor bo‘lsa — o‘tkazib yuboriladi. Yoki operatsiyaning o‘zi idempotent (upsert, set status).
?Saga nima? Choreography va orchestration farqi?›
Bir nechta servisdagi lokal tranzaksiyalar ketma-ketligi; xato bo‘lsa oldingi qadamlar kompensatsiya tranzaksiyalari bilan bekor qilinadi. Choreography — servislar hodisalarga javob beradi (markazsiz); orchestration — markaziy koordinator buyruq beradi va holatni saqlaydi.
?2PC o‘rniga nega Saga?›
2PC (XA) — bloklovchi, koordinator yiqilsa resurslar qulflanib qoladi, Kafka va ko‘p zamonaviy tizimlar qo‘llamaydi, masshtablanmaydi. Saga — eventual consistency evaziga mavjudlik va mustaqillik.
?Compacted topic nima uchun?›
Har kalitning faqat oxirgi qiymatini saqlaydi (va tombstone bilan o‘chiradi) — "holat jurnali": yangi consumer butun holatni topic’dan tiklaydi. __consumer_offsets, KTable, CDC snapshot’lar.
?Schema Registry nima uchun kerak?›
Producer va consumer o‘rtasidagi shartnomani markazlashtirish: xabarda faqat sxema ID’si (5 bayt), sxema registrda; moslik (BACKWARD/FORWARD/FULL) tekshiruvi buzuvchi o‘zgarishni deploy’dan oldin rad etadi; Avro/Protobuf bilan ixcham binar format.
