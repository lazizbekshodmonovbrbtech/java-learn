Grant flow'lar va PKCE

"Grant" — tokenni qanday yo'l bilan olish. Har ilova turi uchun o'z yo'li bor. Mijoz login'i uchun deyarli hamma joyda bitta javob: Authorization Code + PKCE. Bu modulda har bir HTTP so'rov qadamlab ko'rsatiladi. Suhbatda aynan shu ketma-ketlikni doskaga chizish so'raladi.

01

Sequence diagramma — flow'ni tanlang

Qadamlab yuring. Uzluksiz chiziq — brauzer orqali (front-channel), yashil punktir — server'dan server'ga (back-channel). Pastda har qadamning haqiqiy HTTP so'rovi.

02

PKCE — o'zingiz hisoblang

Proof Key for Code Exchange. Ilova tasodifiy code_verifier yaratadi va Keycloak'ka faqat uning hash'ini (code_challenge) yuboradi. Kodni tokenga almashtirishda verifier'ning o'zi yuboriladi. Keycloak hash'lab solishtiradi. Hisoblash quyida brauzeringizning o'zida bajariladi.

03

PKCE nimadan himoya qiladi — kod o'g'irlash hujumi

Telefonga uz.bank.app:// sxemasini ham "egallab olgan" zararli ilova o'rnatilgan. Keycloak kodni redirect qilganda, kod zararli ilovaga tushib qolishi mumkin. Mobil ilova public client — client_secret yo'q. PKCE'ni yoqib-o'chirib hujumni yurgizing.

PKCE o'chiqPKCE yoqilgan (S256)
🎯 Suhbatda
"PKCE nima va nega confidential client'da ham kerak?" — Authorization code interception va code injection hujumlaridan himoya: kodni faqat verifier egasi (kodni so'ragan aynan shu ilova nusxasi) almashtira oladi. OAuth 2.1 va hozirgi xavfsizlik tavsiyalari (RFC 9700) PKCE'ni barcha client'lar uchun talab qiladi. Keycloak'da: client → Advanced → PKCE Method: S256. plain usulini ishlatmang.
04

state va nonce — ikki kichik, lekin majburiy parametr

state → CSRF'dan himoya

Ilova tasodifiy state yaratadi va o'z sessiyasiga yozadi. Callback'da qaytgan state bilan solishtiradi. Mos kelmasa — rad. Aks holda hujumchi o'z kodini sizning brauzeringizga "tiqib", sizni o'z akkauntiga kiritib qo'yishi mumkin (login CSRF).

nonce → ID token replay'dan himoya

nonce /auth so'roviga qo'shiladi va Keycloak uni id_token ichiga yozadi. Ilova ular tengligini tekshiradi. Shu bilan eski yoki boshqa sessiyadan olingan id_token qabul qilinmaydi.

💡 Spring Security'da
spring-boot-starter-oauth2-client state, nonce va PKCE'ni o'zi yaratadi va tekshiradi. Siz faqat issuer-uri, client-id, client-secret va scope yozasiz. Mobilda — AppAuth kutubxonasi (Android/iOS).

07

Suhbat savollari

?Authorization Code flow'ni qadamma-qadam tushuntiring.›
1) Ilova verifier, challenge, state va nonce yaratadi. 2) Brauzerni /auth?response_type=code&client_id&redirect_uri&scope=openid&state&nonce&code_challenge&code_challenge_method=S256 ga yo'naltiradi. 3) Foydalanuvchi Keycloak'da login qiladi (parol faqat Keycloak'ka boradi), SSO sessiya yaratiladi. 4) Keycloak redirect_uri?code&state ga qaytaradi. 5) Ilova state'ni tekshiradi va back-channel'da POST /token qiladi (code, redirect_uri, client auth, code_verifier). 6) Keycloak kodni (bir martalik, qisqa muddatli), redirect_uri'ni va PKCE'ni tekshirib, access, refresh va id token beradi. 7) Ilova id_token'ni tekshiradi (imzo, iss, aud, exp, nonce) va API'ni access token bilan chaqiradi.
?Nega Implicit va Password grant'lar eskirgan?›
Implicit: token URL fragment'ida keladi — brauzer tarixi, kengaytmalar va Referer orqali oqib chiqadi, refresh yo'q, sender binding yo'q. Uning o'rniga Code + PKCE. Password: ilova foydalanuvchi parolini ko'radi, MFA, SSO va tashqi IdP ishlamaydi, foydalanuvchilarni "parolni har joyga kiritish"ga o'rgatadi. OAuth 2.1 ikkalasini ham olib tashlagan.
?SPA (React) uchun qaysi flow va tokenlarni qayerda saqlaysiz?›
Authorization Code + PKCE (public client). Eng xavfsiz arxitektura — BFF: SPA o'z backend'i bilan httpOnly+Secure+SameSite cookie orqali ishlaydi, tokenlar faqat server'da (Spring Cloud Gateway + oauth2Login + TokenRelay). Tokenlar brauzerda bo'lsa — faqat xotirada (localStorage emas, XSS xavfi), refresh rotation bilan.
?Servisdan servisga murojaat qanday himoyalanadi?›
Client Credentials: har servisning o'z client'i va service account'i, minimal rollar, audience cheklovi. Token muddati tugashidan oldin keshda saqlanadi (Spring'da OAuth2AuthorizedClientManager buni avtomatik qiladi). client_secret o'rniga private_key_jwt yoki mTLS ham mumkin. Foydalanuvchi kontekstini uzatish kerak bo'lsa — token exchange.
?Refresh token rotation nima?›
Har refresh'da yangi refresh token beriladi, eskisi bekor qilinadi. Eski token qayta ishlatilsa (o'g'irlanganining belgisi), Keycloak xato qaytaradi va sessiyani bekor qilishi mumkin. Keycloak'da: Realm settings → Tokens → "Revoke Refresh Token" + "Refresh Token Max Reuse = 0".
