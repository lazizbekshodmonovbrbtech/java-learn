03
Strategy — jonli: komissiya siyosati

    
Bitta interfeys, bir nechta amalga oshirish. Strategiyani almashtiring — if/else yo'q, yangi strategiya = yangi klass.

    

      
summa:

      

      

    

    

      
Strategy.java (Spring uslubi)

      
interface KomissiyaSiyosati { BigDecimal hisobla(BigDecimal summa); TolovTuri turi(); }

@Component class KartaKomissiya implements KomissiyaSiyosati { ... turi() { return KARTA; } }
@Component class NaqdKomissiya  implements KomissiyaSiyosati { ... }

@Service class TolovService {
    private final Map<TolovTuri, KomissiyaSiyosati> siyosatlar;
    TolovService(List<KomissiyaSiyosati> list) {           // Spring hamma bean'ni List qilib beradi
        siyosatlar = list.stream().collect(toMap(KomissiyaSiyosati::turi, s -> s));
    }
    BigDecimal komissiya(Tolov t) { return siyosatlar.get(t.turi()).hisobla(t.summa()); }   // switch yo'q
}

Observer — jonli: hodisa va obunachilar

    
To'lov tugadi → SMS, audit, cashback — har biri mustaqil. To'lov servisi ularni bilmaydi. Spring'da: ApplicationEventPublisher + @EventListener.

    

      

        
Tugmani bosing.

        

      

    

    

      
Events.java

      
record TolovTugadi(Long tolovId, BigDecimal summa) {}

// Publisher — kim tinglashini bilmaydi
publisher.publishEvent(new TolovTugadi(t.id(), t.summa()));

// Listener'lar — alohida klasslarda, alohida mas'uliyat
@TransactionalEventListener(phase = AFTER_COMMIT)   // faqat COMMIT bo'lgach — SMS "o'tdi" deb yolg'on gapirmasin

@EventListener @Async

05
Proxy — Spring'ning "sehri" aslida shu

    
@Transactional, @Cacheable, @Async, security — hammasi bean'ni proxy bilan o'rab, chaqiriqni ushlab qoladi. Qadamlab ko'ring.

    

      

      

      

    

    
⚠ Klassik tuzoq (30-modulda ham)
Bir klass ichida this.otkazma() chaqirsangiz — proxy chetlab o'tiladi, @Transactional ishlamaydi. Sabab: proxy tashqaridan kelgan chaqiriqni ushlaydi, this — asl obyekt. Yechim: boshqa bean'ga ajratish.

  


  

    
06
Suhbat savollari

    

      
?SOLID'ni bir jumladan tushuntiring.›
S — klass bitta sabab bilan o'zgarsin. O — yangi xususiyat = yangi kod, eski kodni o'zgartirmasdan (interface + yangi implementatsiya). L — bola klass ota o'rnida ishlatilsa hech narsa buzilmasin. I — mijozga kerak bo'lmagan metodni majburlamang (kichik interface'lar). D — yuqori daraja abstraksiyaga bog'lansin, konkret klassga emas (DI shundan).

      
?Spring'da qaysi pattern'lar bor?›
Singleton — bean scope default. Factory — BeanFactory/ApplicationContext, @Bean metodlari. Proxy — AOP, @Transactional, @Cacheable. Template Method — JdbcTemplate, RestTemplate (resurs ochish/yopish shablon, siz faqat mantiq). Observer — ApplicationEvent. Strategy — interface + List<Impl> inject. Builder — UriComponentsBuilder, RestClient.builder(), Lombok @Builder. Adapter — HandlerAdapter (MVC). Decorator — BufferedReader(new FileReader), Servlet filter zanjiri. Front Controller — DispatcherServlet.

      
?Singleton pattern va Spring singleton bean farqi?›
GoF Singleton — klass o'zi bitta nusxani kafolatlaydi (private ctor + static getInstance), JVM bo'yicha bitta, testlash qiyin, global holat. Spring singleton — container bitta nusxa saqlaydi (ApplicationContext bo'yicha), klass oddiy, test uchun mock bilan almashtiriladi. Spring'da qo'lda Singleton yozish — anti-pattern.

      
?Liskov'ni buzgan mashhur misol?›
Square extends Rectangle: setWidth(5) kvadratda balandlikni ham o'zgartiradi — Rectangle kutgan xatti-harakat buziladi. Java'dan: Collections.unmodifiableList — List interfeysi, lekin add() UnsupportedOperationException (ataylab qilingan murosa). Belgi: bola klass ota metodini "bo'sh" yoki exception bilan override qilsa — LSP buzilgan.

      
?Anemic domain model nima?›
Entity faqat getter/setter, butun mantiq Service'da — obyekt "qonsiz". Muqobil: rich domain — hisob.yech(summa) o'zi tekshiradi va holatini o'zgartiradi, Service faqat orkestratsiya. Bank domenida rich model invariantlarni (balans ≥ 0) bir joyda ushlaydi.

      
?Pattern'ni qachon ishlatmaslik kerak?›
Muammo yo'q joyda. Ikkita implementatsiya bo'lmasa Strategy ortiqcha; oddiy 3 maydonli obyekt uchun Builder ortiqcha. Qoida: avval oddiy kod, takrorlanish/o'zgarish og'rig'i paydo bo'lganda refactor → pattern. "Pattern uchun pattern" — over-engineering.
