Spring Kafka

Spring for Apache Kafka poll sikli, commit, thread’lar va xatolarni boshqarishni o‘z zimmasiga oladi — sizga faqat @KafkaListener metodi qoladi. Lekin default sozlamalar bankka mos emas: xato bo‘lgan xabar jim tashlab yuborilishi mumkin. Bu modulda listener konteyneri, retry strategiyalari va Dead Letter Topic’ni simulyatorda ko‘ramiz.

01

Listener va konteyner

application.yml
spring:
  kafka:
    bootstrap-servers: kafka-1:9092,kafka-2:9092,kafka-3:9092
    consumer:
      group-id: sms-service
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer
        spring.json.trusted.packages: uz.bank.events
        max.poll.records: 100
        isolation.level: read_committed
    listener:
      ack-mode: record            # har xabardan keyin commit (default: batch)
      concurrency: 3              # 3 ta consumer thread
SmsListener.java
@Component
@RequiredArgsConstructor
class SmsListener {
    private final SmsService sms;

    @KafkaListener(topics = "tolovlar", groupId = "sms-service")
    void on(PaymentEvent ev,
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
            @Header(KafkaHeaders.OFFSET) long offset) {
        sms.sendOnce(ev.paymentId(), ev.phone(), ev.text());   // idempotent: paymentId bo'yicha
    }
    // metod xatosiz tugasa — konteyner offset'ni commit qiladi (ack-mode bo'yicha)
    // exception otilsa — ErrorHandler ishga tushadi (quyida)
}
concurrency: 3 (topic’da 6 partition, 2 ta pod)

StrategiyaAfzallikKamchilikQachon
Default DefaultErrorHandler (FixedBackOff 0 ms × 9)—10 urinish bir zumda, keyin log va o‘tkazib yuborish — xabar yo‘qoladiHech qachon (sozlang!)
Blocking: DefaultErrorHandler + ExponentialBackOff + DeadLetterPublishingRecovererTartib saqlanadiRetry paytida partition to‘xtaydi; uzoq backoff max.poll.interval’ga yaqinlashadiTartib muhim (hisob hodisalari), qisqa retry
Non-blocking: @RetryableTopicAsosiy oqim to‘xtamaydi; uzoq kechikishlar mumkinTartib buziladi; qo‘shimcha topic’larMustaqil xabarlar (SMS, push, email)
KafkaErrorConfig.java — blocking
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template,
        (rec, ex) -> new TopicPartition(rec.topic() + "-dlt", rec.partition()));   // xuddi shu partition
    var backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1_000);
    backoff.setMultiplier(2.0);                                                    // 1 s, 2 s, 4 s
    var h = new DefaultErrorHandler(recoverer, backoff);
    h.addNotRetryableExceptions(ValidationException.class,                         // qayta urinishdan foyda yo'q
                                DeserializationException.class);
    return h;                                                                      // Boot uni konteynerga ulaydi
}
SmsListener.java — non-blocking
@RetryableTopic(
    attempts = "3",
    backoff = @Backoff(delay = 1_000, multiplier = 5.0),        // retry-0: 1 s, retry-1: 5 s
    exclude = { ValidationException.class },                    // bular darhol DLT'ga
    dltStrategy = DltStrategy.FAIL_ON_ERROR)
@KafkaListener(topics = "tolovlar", groupId = "sms-service")
void on(PaymentEvent ev) { sms.sendOnce(ev.paymentId(), ev.phone(), ev.text()); }

@DltHandler
void dlt(PaymentEvent ev, @Header(KafkaHeaders.EXCEPTION_MESSAGE) String err) {
    alerts.raise("SMS DLT", ev.paymentId(), err);               // monitoring + qo'lda ko'rib chiqish
}
🎯 DLT’dagi xabarlar bilan nima qilinadi?
DLT — axlat qutisi emas, navbat. Uni kuzatish (alert, dashboard) va qayta ishlash jarayoni bo‘lishi kerak: xato sababini tuzatgach, DLT’dan asosiy topic’ga qayta yuborish (replay tool) yoki qo‘lda hal qilish. Header’larda asl topic, partition, offset va exception saqlanadi (kafka_dlt-original-offset, kafka_dlt-exception-message).

Batch listener, qo‘lda ack, tranzaksiya

BatchListener.java
@KafkaListener(topics = "tolovlar", groupId = "analytics", batch = "true")
void onBatch(List<PaymentEvent> events) {
    repo.saveAll(events.stream().map(Mapper::toRow).toList());   // 500 ta bitta INSERT batch — 50x tez
}

@KafkaListener(topics = "kartalar", groupId = "card-block")
void onManual(CardEvent ev, Acknowledgment ack) {                 // ack-mode: manual
    cardService.block(ev.cardId());
    ack.acknowledge();                                            // aynan shu yerda commit
}
Transfer.java — read-process-write (Kafka ichida exactly-once)
spring.kafka.producer.transaction-id-prefix: p2p-tx-      # transaksional producer yoqiladi

@KafkaListener(topics = "p2p-sorovlar")
@Transactional("kafkaTransactionManager")
void on(P2pRequest r) {
    kafka.send("p2p-natijalar", r.id(), process(r));     // chiqish xabari va kirish offset commit'i
}                                                        // bitta Kafka tranzaksiyasida
⚠️ Kafka tranzaksiyasi DB’ni qamramaydi
@Transactional bilan DB va Kafka tranzaksiyalarini birlashtirib bo‘lmaydi (XA/2PC qo‘llab-quvvatlanmaydi). DB commit bo‘lib Kafka commit bo‘lmasligi (yoki aksincha) mumkin. DB + hodisa atomikligi uchun — Transactional Outbox (63-modul); consumer tomonida — idempotentlik.

💡 @EmbeddedKafka yoki Testcontainers?
@EmbeddedKafka — JVM ichida, tez, Docker kerak emas; lekin haqiqiy broker’dan farqlari bor. Testcontainers — haqiqiy Kafka, CI’da Docker kerak. Integratsion testlar uchun Testcontainers + @ServiceConnection (Boot 3.1+) — eng ishonchli.
05

Suhbat savollari

?@KafkaListener metodida exception otilsa nima bo‘ladi?›
Konteyner ErrorHandler’ni chaqiradi. Default DefaultErrorHandler: FixedBackOff(0, 9) — 10 urinish, keyin log va o‘tkazib yuborish (offset commit), ya’ni xabar yo‘qoladi. Production’da backoff va DeadLetterPublishingRecoverer sozlanadi, qayta urinishdan foyda yo‘q exception’lar not-retryable qilinadi.
?Blocking va non-blocking retry farqi?›
Blocking — xabar o‘z joyida qayta uriniladi (seek), partition’dagi keyingi xabarlar kutadi, tartib saqlanadi. Non-blocking — xabar retry topic’ga ko‘chiriladi, asosiy oqim davom etadi, lekin tartib buziladi. Tartib muhim bo‘lsa — blocking; mustaqil xabarlar — non-blocking.
?Deserializatsiya xatosi (noto‘g‘ri JSON) qanday hal qilinadi?›
ErrorHandlingDeserializer bilan: delegate deserializer xato bersa, exception konteynerga header’da uzatiladi, listener chaqirilmaydi, ErrorHandler uni not-retryable deb darhol DLT’ga yuboradi. Aks holda consumer shu offset’da cheksiz aylanib qoladi.
?concurrency nima va nechta qo‘yish kerak?›
Bitta ilova instance’ida nechta KafkaConsumer (thread) ishlashi. Umumiy consumer soni = pod × concurrency; u partition sonidan oshsa ortiqchasi bo‘sh. Odatda partitions / pods.
?Listener’da DB va Kafka’ga yozish atomik bo‘ladimi?›
Yo‘q — ular alohida tranzaksiyalar. Kafka’ning o‘z tranzaksiyasi faqat Kafka ichidagi read-process-write’ni atomik qiladi. DB bilan: Outbox pattern yoki idempotent consumer + DB tranzaksiyasi ichida "processed" jadvali.
?Kafka listener’ni qanday test qilasiz?›
Unit: listener metodini oddiy metod sifatida. Integratsion: Testcontainers Kafka + @ServiceConnection, KafkaTemplate bilan yuborib, Awaitility bilan natijani kutish; DLT uchun — noto‘g‘ri xabar yuborib, DLT topic’dan o‘qish.
