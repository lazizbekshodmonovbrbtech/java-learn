@Transactional chuqur

A hisobdan pul chiqdi, B hisobga kirmadi — server o'rtada yiqildi. Tranzaksiya buni imkonsiz qiladi: "hammasi yoki hech narsa". Lekin @Transactional qanday ishlaydi, qachon ishlamaydi — bu suhbatlarda eng ko'p so'raladigan Spring mavzusi.

01

Atomiklik: o'tkazma o'rtasida server yiqildi

A → B ga 300 so'm. Qadam 2 (B'ga qo'shish) da xato bo'ladi. @Transactional bilan va busiz kuzating:

Hisob A
1000
→ 300 →
Hisob B
500
BEGIN
UPDATE account SET balance = balance - 300 WHERE id = A
UPDATE account SET balance = balance + 300 WHERE id = B ← 💥 xato
INSERT INTO transfer (...)
COMMIT / ROLLBACK
Jami pul: 1500
Bank invarianti: A + B = 1500 har doim. Ishga tushiring.
TransferService.java
@Service
public class TransferService {
    @Transactional                                      // public metod, Spring bean, tashqaridan chaqiriladi
    public void transfer(Long from, Long to, BigDecimal amt) {
        Account a = accRepo.findByIdForUpdate(from);   // SELECT ... FOR UPDATE (36-modul)
        Account b = accRepo.findByIdForUpdate(to);
        if (a.getBalance().compareTo(amt) < 0) throw new InsufficientFundsException();
        a.debit(amt);  b.credit(amt);                    // dirty checking → 2 UPDATE
        transferRepo.save(new Transfer(a, b, amt));
    }                                                   // exception yo'q → COMMIT; RuntimeException → ROLLBACK
}
02

Proxy: annotatsiya qanday ishlaydi va qachon ishlamaydi

Spring sizning bean'ingizni proxy bilan o'raydi. Tashqaridan chaqiruv proxy orqali keladi → proxy tranzaksiya ochadi → real metod → commit. Lekin klass ichidan this.metod() — proxy'ni chetlab o'tadi. Ikkisini solishtiring:

Chaqiruvchi
service.transfer(...)
this.audit(...)
Proxy (Spring yaratgan)
tx = begin()
target.metod()
commit() / rollback()
tx: —
TransferService (real)
transfer() { ... }
@Transactional(REQUIRES_NEW) audit()
@Transactional ishlamaydigan holatlar
1) Self-invocation — this.metod(). 2) private/protected/final metod — proxy override qila olmaydi (CGLIB). 3) Interface'siz final klass. 4) Bean bo'lmagan obyekt (new Service()). 5) Exception ichkarida catch qilinib yutildi — Spring xatoni ko'rmaydi. 6) Checked exception — default rollback bo'lmaydi (pastda). 7) Boshqa thread (@Async, CompletableFuture) — tranzaksiya thread-bound (ThreadLocal). Yechim (1) uchun: mantiqni alohida bean'ga ajrating yoki TransactionTemplate.
03

Propagation: ichki metod o'z tranzaksiyasini ochadimi?

transfer() (REQUIRED) ichida auditLog() chaqiriladi va auditLog exception tashlaydi (yoki transfer keyin yiqiladi). Audit yozuvi saqlanadimi? Propagation'ni tanlang:

Amaliy qoida
Deyarli doim REQUIRED (default). REQUIRES_NEW — asosiy ish yiqilsa ham saqlanishi kerak bo'lgan narsalar: audit log, "urinish" yozuvi, xabar navbati. Ehtiyot: REQUIRES_NEW ikkinchi DB ulanishini oladi — pool'da 2 ta band, deadlock xavfi (tashqi tx qulflagan qatorni ichki tx kutadi). NESTED — savepoint, faqat JDBC (JPA'da ishlamaydi).
04

Rollback qoidalari: checked exception tuzog'i

Metod exception tashladi. Spring rollback qiladimi? Default qoida ko'pchilikni hayron qoldiradi. Exception turini tanlang:

Sozlamalar
@Transactional(
    rollbackFor = Exception.class,          // checked'da ham rollback — bank uchun tavsiya
    readOnly = true,                      // o'qish: dirty checking o'chadi, Hibernate flush yo'q, replica'ga yo'naltirish
    timeout = 5,                          // soniya — uzoq tranzaksiya lock ushlab turadi
    isolation = Isolation.READ_COMMITTED, // Postgres default (36-modul)
    propagation = Propagation.REQUIRED)
public ...

// Dasturiy usul — aniq chegara, self-invocation muammosi yo'q:
private final TransactionTemplate tx;
tx.execute(status -> { ...; if (bad) status.setRollbackOnly(); return r; });

// Commit'dan KEYIN ish (email, Kafka) — tx ichida emas:
@TransactionalEventListener(phase = AFTER_COMMIT)
void onTransfer(TransferCompleted e) { sms.send(...); }   // rollback bo'lsa SMS ketmaydi ✓
05

Suhbat savollari

?@Transactional qanday ishlaydi?
Spring bean'ni proxy (JDK dynamic — interfeys bo'lsa, yoki CGLIB subclass) bilan o'raydi. Chaqiruv proxy'ga keladi → TransactionInterceptor → PlatformTransactionManager.getTransaction() (ulanish olinadi, autocommit=false, ThreadLocal'ga bog'lanadi) → real metod → normal tugasa commit, RuntimeException/Error bo'lsa rollback → ulanish pool'ga qaytadi. Repository'lar o'sha ThreadLocal ulanishni ishlatadi.
?Self-invocation muammosi nima?
Klass ichida this.otherMethod() — proxy chetlab o'tiladi, this real obyekt. otherMethod'dagi @Transactional (REQUIRES_NEW, readOnly...) e'tiborsiz. Yechim: mantiqni boshqa bean'ga ajratish, o'z proxy'sini inject qilish (ObjectProvider / @Lazy self), TransactionTemplate, yoki AspectJ weaving (kam).
?Checked exception'da rollback bo'ladimi?
Yo'q — default faqat RuntimeException va Error rollback qiladi; checked exception'da commit. Sabab: EJB konventsiyasi (checked = kutilgan biznes holati). Yechim: rollbackFor = Exception.class, yoki custom exception'larni RuntimeException'dan meros qilish (Spring o'zining DataAccessException'i ham unchecked).
?REQUIRED va REQUIRES_NEW farqi? REQUIRES_NEW xavfi?
REQUIRED — mavjud tx bo'lsa qo'shiladi, yo'q bo'lsa ochadi (bitta taqdir). REQUIRES_NEW — tashqini to'xtatib (suspend) yangi mustaqil tx va yangi DB ulanish ochadi; ichki commit tashqi rollback'dan mustaqil. Xavf: 2 ulanish band (pool tugashi), tashqi tx ushlab turgan qatorni ichki tx kutsa — deadlock/timeout; ichki commit bo'lib tashqi rollback bo'lsa — mantiqiy nomuvofiqlik.
?Ichki metod exception tashladi, tashqi catch qildi. Commit bo'ladimi?
Ikkalasi REQUIRED (bitta tx) bo'lsa — yo'q: ichki proxy tx'ni rollback-only deb belgilaydi, tashqi commit qilmoqchi bo'lganda UnexpectedRollbackException. Ichki REQUIRES_NEW bo'lsa — tashqi davom etadi va commit bo'ladi. Ichki metod proxy orqali chaqirilmagan bo'lsa (this.) — belgilanmaydi, tashqi commit bo'ladi.
?readOnly = true nima beradi?
Hibernate: session flush mode MANUAL — dirty checking/flush yo'q (tezroq, snapshot saqlanmaydi, xotira kam). JDBC: connection.setReadOnly(true) — drayver/DB optimallashtirishi, Postgres'da yozish urinishi xato. Routing DataSource'da o'qishni replica'ga yo'naltirish. Bu 'himoya' emas — asosan optimallashtirish; yozish urinishi Hibernate'da jimgina yo'qolishi mumkin.
?Tranzaksiya ichida tashqi HTTP/Kafka/email chaqirish nega yomon?
Tranzaksiya ochiq — DB ulanish va lock'lar band; tashqi servis sekin bo'lsa pool tugaydi, lock'lar uzoq turadi. Rollback bo'lsa email allaqachon ketgan (qaytarib bo'lmaydi). Yechim: @TransactionalEventListener(AFTER_COMMIT), transactional outbox pattern (jadvalga yozib, alohida process yuboradi), tashqi chaqiruvni tx'dan tashqariga chiqarish.
?Tranzaksiya va @Async / yangi thread?
Tranzaksiya ThreadLocal'ga bog'liq — yangi thread'da tx yo'q (va ThreadLocal ulanish yo'q). @Async metod o'z @Transactional'ini ochishi mumkin, lekin chaqiruvchining tx'sidan mustaqil. Parallel stream ichida repository chaqirish — har thread alohida ulanish, tx'siz. Yechim: har thread o'z tx'i (TransactionTemplate) yoki ishni tx tashqarisida parallel qilish.
?Tranzaksiya chegarasi qayerda bo'lishi kerak?
Service qatlamida (use-case): bitta biznes amal = bitta tx. Controller'da emas (HTTP bilan aralashadi, OSIV). Repository'da emas (juda mayda — har save alohida tx, atomiklik yo'q). Uzoq tx yomon — timeout qo'ying, katta batch'larni bo'laklab (chunk) alohida tx'larda bajaring.
?Testda @Transactional nima qiladi?
@SpringBootTest/@DataJpaTest'da test metodi @Transactional bo'lsa — test oxirida avtomatik ROLLBACK (baza toza qoladi). Tuzoq: flush hech qachon bo'lmasligi mumkin (constraint xatolari ko'rinmaydi) — saveAndFlush yoki TestEntityManager.flush(); LAZY yuklash testda ishlab prod'da LazyInitializationException berishi mumkin (testda sessiya ochiq). @Commit / @Rollback(false) bilan o'zgartirish mumkin.
06

O'zingizni tekshiring

1.@Transactional metod IOException (checked) tashladi. Natija?
2.Service ichida this.helper() chaqirildi, helper @Transactional(REQUIRES_NEW). Yangi tx ochiladimi?
3.Transfer (REQUIRED) → audit (REQUIRES_NEW) commit bo'ldi, keyin transfer yiqildi. Audit yozuvi?
4.Ichki REQUIRED metod RuntimeException tashladi, tashqi catch qilib davom etdi, oxirida commit. Nima bo'ladi?
5.Pul o'tkazmasi tranzaksiya chegarasi qayerda bo'lishi kerak?
6.Tranzaksiya ichida SMS yuborildi, keyin rollback. Eng to'g'ri yechim?
